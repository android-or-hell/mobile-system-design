아래처럼 **볼드 처리한 내용을 중심으로만 남기고**, 중복 설명과 예시는 줄여서 핵심 흐름이 이어지도록 정리할 수 있습니다.

# 2 재사용 가능한 뷰 제공하기: 디자인을 분해하는 기술

> **가장 강력한 뷰는 자신이 어디에 사용되는지 알지 못하는 뷰다.**

화면을 구현할 때는 단순히 화면 하나를 만드는 데 그치지 않고, **화면을 구현하는 동시에 건강한 UI 라이브러리까지 함께 구축하는 것**을 목표로 한다.

이를 위해서는 뷰의 **이름과 추상화 수준**을 신중하게 판단해야 한다.

---

## 2.1 뷰를 어떻게 사용하는지가 아니라, 그 뷰가 무엇인지에 따라 이름을 지어라

**대부분의 뷰는 자신이 어떤 기능에 속해 있는지 알 필요가 없다.**

뷰 타입에 지나치게 구체적인 이름을 붙이면 재사용성이 떨어지고, 비슷하지만 조금씩 다른 뷰가 계속 늘어난다. 또한 뷰가 자신이 어떻게 사용되는지 지나치게 많이 알게 되면 특정 상황에만 사용할 수 있는 복잡한 ‘스마트한 뷰’가 되기 쉽다.

### 타입 이름과 사용 목적을 분리한다

`TutorView`나 `ProfileView` 같은 이름은 현재 사용 목적을 타입 이름에 드러낸다.

대신 `ImageLabelView`처럼 **뷰 자체가 무엇인지를 나타내는 일반적인 이름**을 사용한다.

```swift
let tutorView = ImageLabelView(
    image: avatar,
    title: "Caleb Davis",
    subtitle: "@CalebGuitar"
)
```

특정 사용 목적은 타입이 아니라 `tutorView`, `profileView` 같은 **인스턴스 이름**으로 표현할 수 있다.

프로퍼티 역시:

```text
avatar       → image
displayName  → title
handle       → subtitle
```

처럼 특정 사용 사례에서 분리한다.

중요한 점은 **뷰의 기능을 바꿔 미래를 대비하는 것이 아니라, 현재의 사용 방식과 분리된 이름을 붙이는 것뿐**이라는 점이다.

---

## 2.1.4 뷰 프리미티브

`ImageLabelView`처럼 자신을 사용하는 기능에 대해 알지 못하는 단순한 뷰를 **뷰 프리미티브(View Primitive)**라고 볼 수 있다.

복잡한 데이터 모델을 `String`, `Array` 같은 기본 요소로 만드는 것처럼, 복잡한 UI도 여러 뷰 프리미티브를 조합해 만들 수 있다.

이런 뷰는 특정 기능에 종속되지 않으므로 **UI Library에 둘 수 있다.**

---

## 2.1.5 지나치게 구체적인 뷰를 피한다

특정 사용 사례에 맞춰 뷰를 계속 확장하면:

```text
displayName
handle
firstName
lastName
registeredDate
...
```

처럼 점점 많은 도메인 지식을 갖게 된다.

그러면 **뷰의 독립성이 훼손되고, 뷰가 자신이 어떻게 사용되는지 알기 시작한다.**

결국 부모나 특정 데이터 모델과 강하게 결합되어 재사용성이 떨어질 수 있다.

---

# 2.2 새로운 타입을 만들지 않고 추상화 도입하기

공용 뷰를 일반적으로 유지하더라도, 특정 기능에서는 `displayName`, `handle`처럼 **사용 사례에 잘 맞는 API가 더 편리할 수 있다.**

이때 새로운 `TutorView` 타입을 만들지 않고도 팩토리를 이용할 수 있다.

```swift
let tutorView: ImageLabelView = CourseUI.makeTutorView(
    avatar: avatar,
    displayName: "Caleb Guitar",
    handle: "@CalebGuitar"
)
```

즉, **재사용 가능한 `ImageLabelView`는 그대로 유지하면서 Course 기능 내부에서는 Tutor에 맞는 API를 제공한다.**

```swift
static func makeTutorView(
    avatar: Image,
    displayName: String,
    handle: String
) -> ImageLabelView
```

이렇게 하면 새로운 타입을 만들지 않고도 **기능 내부에 로컬 추상화**를 만들 수 있다.

---

# 2.4 뷰의 스타일을 기준으로 이름을 짓지 마라

뷰의 이름은 현재 사용 목적뿐만 아니라 **현재의 시각적 스타일에서도 분리하는 것이 좋다.**

예를 들어 `SpeechBubble`은 특정 시각적 표현인 ‘말풍선’을 이름에 고정한다.

반면 `CalloutView`는 말풍선, 아이콘과 텍스트 등 어떤 형태로 표현되더라도 **내용을 강조해 전달한다는 의미**를 유지할 수 있다.

> **UI 스타일과 이름을 분리하라.**

즉, 디자인이 바뀌어도 의미가 유지되는 이름을 사용하는 것이 좋다.

또한 재사용성을 높이겠다는 이유로 모든 가능성을 미리 지원할 필요는 없다.

**실제로 필요할 때만 뷰를 설정 가능하게 만든다.**

---

# 2.5 스마트한 뷰보다 조합을 선호하라

모든 뷰를 재사용 가능하게 만들 필요는 없다.

예를 들어 `ScheduleView`는 현재 기능에 지나치게 특화되어 있으므로 일반적인 UI Library 컴포넌트로 만들 필요가 없다.

대신:

> **`ScheduleView` 자체를 재사용 가능하게 만드는 것이 아니라, 내부를 분해해서 재사용 가능한 부분만 추출한다.**

예를 들어:

```text
ScheduleView
├─ AccessoryButton
├─ TextButton
├─ Label
└─ Icon
```

처럼 구성할 수 있다.

`ScheduleView`는 Course 기능에 두고, 일반적인 `AccessoryButton`, `TextButton`은 UI Library에 둔다.

---

## 2.5.2 Todo 목록을 Selection으로 바라보기

현재 기능에서는 Todo 목록으로 사용하고 있지만, UI 자체가 제공하는 것은 **여러 항목 중 선택할 수 있는 목록**이다.

따라서 `TodoListView`가 아니라 더 일반적인 관점에서 `SelectionView`라고 이름 지을 수 있다.

```text
TodoListView
    ↓
SelectionView
```

`TodoList` 도메인은 API 호출, Todo 초기화, 주간 Todo 등 더 높은 수준의 업무를 알고 있으므로 그대로 유지한다.

반면 `SelectionView`는 그 목표를 달성하기 위해 사용하는 더 낮은 수준의 **Selection 프리미티브**다.

---

## 2.5.4 복잡성은 설정이 아니라 조합으로 만든다

제목, 섹션, Reset 버튼 등 모든 경우를 하나의 뷰가 설정으로 처리하도록 만들면 **강한 의견을 가진 스마트한 뷰**가 된다.

이런 뷰는:

* 재사용성이 떨어지고
* 복잡해지며
* 유지보수가 어려워지고
* 다른 개발자가 우회 방법을 사용하게 만들 수 있다.

따라서:

> **복잡성을 만들 때는 조합(composition)을 선호한다.**

단순한 뷰 프리미티브들을 조합해서 복잡한 화면을 만든다.

예를 들어 `SelectionView`는 선택 가능한 행만 관리하고, 제목이나 `reset` 버튼은 화면에서 별도로 조합한다.

---

## 2.5.6 가상의 미래 상황을 위해 구현하지 마라

현재 `SelectionView`에 다중 선택만 필요하다면 그것만 제공한다.

나중에 실제로 단일 선택이 필요해졌을 때 추가하면 된다.

미래에 다른 개발자가 필요할지도 모른다는 이유로 미리 기능을 넣지 않는다.

> **우리는 가상의 미래 상황을 위해 개발하고 있는 것이 아니다.**

> **그렇게 하는 것이 바로 오버엔지니어링이다.**

---

## 2.5.7 버튼의 이름도 의미를 기준으로 생각한다

`BorderButton`처럼 외형을 이름에 넣으면 미래에 테두리가 사라졌을 때 이름이 맞지 않게 된다.

따라서 **기능적인 의미**를 생각한다.

```text
BorderButton ❌

SubduedButton ✅
```

`SubduedButton`은 상대적으로 덜 강조되는 버튼이라는 의미를 표현한다.

따라서 테두리가 없어지거나 밑줄 스타일로 바뀌더라도 이름은 그대로 유지할 수 있다.

---

# 2.6 최종 구조

화면을 분해하면 크게 두 종류의 뷰가 남는다.

### 재사용 가능한 뷰 프리미티브 — UI Library

* `ImageLabelView`
* `CalloutView`
* `AccessoryButton`
* `TextButton`
* `SelectionView`
* `SelectionItemView`
* `SubduedButton`

### 기능에 특화된 뷰 — Course

* `CourseView`
* `ScheduleView`

이를 통해 **재사용 가능한 UI Library는 계속 성장시키면서, 기능에 특화된 복잡성은 해당 기능 안에 유지할 수 있다.**

---

# 2.7 핵심 정리

대부분의 공용 뷰는 `Course`, `Tutor`, `Todo` 같은 특정 사용 맥락을 알 필요가 없다.

이런 단순하고 일반적인 뷰를 **뷰 프리미티브**로 만들고 조합해서 더 복잡한 UI를 구성한다.

중요한 것은 **“나중에 재사용할 수도 있으니까” 기능을 추가하는 것이 아니다.**

> **이름을 사용 목적에서 분리하고, 뷰를 적절한 크기로 분해한 결과 자연스럽게 재사용 가능해지는 것이다.**

재사용 가능한 뷰는 UI Library에 두고, 특정 기능에 종속된 뷰는 해당 기능 가까이에 둔다.
