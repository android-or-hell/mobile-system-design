# UI 03 뷰·컴포넌트·화면 정리 — 무엇을 아는가가 뷰의 자리를 정한다

> Mobile System Design 시리즈 Book 1 (Modular UI & UI Architectures) 의 세 번째 챕터.
> 핵심 질문: *뷰가 비즈니스 로직을 알아야 하는 때는 언제이고, 그 앎은 어느 뷰 하나에 모아 두어야 하는가?*

---

## 도입 — 바인딩의 세계로 들어가기

챕터는 농담 섞인 질문으로 시작한다.

> **(p.47)** *"오래된 철학자들이 세월에 걸쳐 답하려 한 질문이 있습니다. **컴포넌트가 먼저인가, 뷰가 먼저인가?**"*

Chapter 2는 뷰를 "모르게" 만드는 데 집중했다. 그 결과 대부분의 뷰가 데이터도 로직도 거의 없는 상태로 UI 라이브러리에 자리 잡았다.

> **(p.47)** *"이전 챕터에서 우리는 기능, 즉 화면을 만드는 데 쓸 뷰들을 만들었습니다. 도입한 대부분의 뷰는 '멍청한'(또는 **뷰 프리미티브**) 상태로 유지했습니다. 데이터나 로직을 많이 담지 않는다는 뜻입니다."*
>
> *"또한 적합한 이름을 붙이는 데 각별히 주의를 기울였습니다. 그 결과 그 뷰들은 재사용성이 매우 높고, 자신이 쓰이는 기능을 알지 못하며, 이제 UI 라이브러리에 살 수 있습니다."*

그러나 고객이 실제로 쓰는 기능을 만들려면, 어딘가에서는 뷰와 비즈니스 로직이 만나야 한다.

> **(p.47)** *"그러나 고객 대면 기능을 이야기하는 순간, UI는 갑자기 비즈니스 로직의 일부가 됩니다. 이것을 작동시키려면 모델 레이어의 `Course`나 `Tutor` 같은 데이터와 로직을 특정 뷰에 연결해야 합니다. 즉 뷰와 비즈니스 로직을 **둘 다** 아는 코드 조각이 필요합니다."*
>
> *"이제 우리는 **바인딩**의 세계로 들어갑니다. 완전히 작동하는 UI를 갖추기 위해 뷰를 데이터와 사용자 입력에 연결하는 행위입니다."*
>
> *"MVC의 컨트롤러든, MVVM이든, 선언형 프레임워크의 상태 처리든, 어떤 아키텍처나 패러다임을 선호하든 요지는 같습니다. 사용자 입력을 받고, 데이터 변경에 반응하고, 뷰가 알맞은 최신 데이터를 보여주도록 보장하는 것입니다. 가능하면 매끄러운 프레임 레이트를 유지하면서요."*

이 한 문단이 챕터 전체의 문제의식이다. Chapter 2까지는 "무엇을 모르게 할 것인가"만 따졌다면, 이 챕터는 "그렇다면 누가 알아야 하는가"를 따진다. 저자는 이 문제를 네 단계로 다루겠다고 예고한다.

> **(p.48)** *"이를 체계적으로 다루기 위해, 먼저 뷰를 세 범주로 분류할 것입니다. 뷰 프리미티브, 뷰 컴포넌트, 기능 뷰입니다. 이 분류는 뷰가 언제 비즈니스 로직을 알아야 하고 어디에 살아야 하는지를 이해하는 데 도움이 됩니다."*
>
> *"다음으로 재사용성을 탐구합니다. 언제 뷰를 재사용 가능하게 만들어야 하는가? 미리 재사용 가능하게 만들면 과잉 설계의 위험이 있지만, 올바르게 하면 속도와 유연성을 유지할 수 있습니다."*
>
> *"그런 다음 바인딩 접근을 검토합니다. 뷰를 비즈니스 로직에 어떻게 연결해야 하는가? 뷰모델을 쓰는가? 언제 그것이 과도한 오버헤드가 되는가? 선언형과 명령형 해법을 모두 다룹니다."*
>
> *"마지막으로 철학적인 태도로 '화면'의 역할을 다룹니다. '똑똑한' 기능과 '멍청한' 뷰를 혼동하게 만들 수 있는 용어입니다."*

그리고 이 챕터가 앞 챕터들과 형식이 다르다는 점도 미리 밝혀 둔다.

> **(p.48)** *"이 챕터에는 다이어그램이 많고 코드는 없습니다. 다음 챕터는 그 반대이며, 여기서 정의한 접근을 사용해 실제 구현을 작성할 것입니다."*

그래서 이 정리 문서에도 책의 코드는 없다. 대신 도해가 말하는 의존 방향을 문장으로 옮겨 두고, 끝의 "안드로이드로 옮기면" 절에서 Compose 코드로 보충한다.

## 세 분류와 다섯 원칙이 이루는 지도

Chapter 2의 원칙 5·6·7이 하나의 분해 절차였듯, 이 챕터의 원칙 8~12도 **하나의 분류 체계를 세우고 그 경계를 시험하는 과정**이다.

먼저 챕터가 세우는 세 분류를 한 표로 정리하면 다음과 같다.

| 분류 | 로직·바인딩 | 기능(비즈니스 로직)을 아는가 | 기본 거처 | 이 챕터의 예 |
|---|---|---|---|---|
| **뷰 프리미티브** | 없거나 최소 | 모른다 | UI 라이브러리 (예외: 원칙 10) | `ImageLabelView`, `TextButton`, `ScheduleView`, 제목과 버튼뿐인 전체 화면 알림 |
| **뷰 컴포넌트** | 있다 ("똑똑하다") | 모른다 | UI 라이브러리 | `SelectionView`, 날짜 피커, 사진 피커, 강등된 `CourseView` |
| **기능 뷰** | 있다 | **안다** | 기능 도메인 | `CourseView`, `CourseViewController` |

다섯 원칙은 이 표의 각 칸을 하나씩 확정한다.

| 절 | 원칙 | 맡은 역할 | 한 문장 |
|---|---|---|---|
| §3.1 | **원칙 8** | **정의** — 새 범주의 도입 | 로직이나 바인딩을 가진 뷰는 프리미티브가 아니라 컴포넌트다 |
| §3.2 | **원칙 9** | **제약** — 컴포넌트의 경계 | 컴포넌트는 똑똑해도 비즈니스 로직은 모른다. 인터페이스로 끊는다 |
| §3.3~3.4 | — | **비용 판단** | 재사용성은 확률이 아니라 투자와 복잡도로 판단한다 |
| §3.5 | **원칙 10** | **예외** — 거처와 앎의 분리 | 기능 안에 사는 뷰라도 기능을 몰라야 한다 |
| §3.6~3.8 | **원칙 11** | **연결** — 앎을 모으는 자리 | 비즈니스 로직과 UI가 만나는 곳이 기능 뷰이고, 그 연결 방식은 여러 가지다 |
| §3.9 | **원칙 12** | **용어 정리** | "화면"은 크기가 아니라 기능성의 문제이므로, 분류 기준으로 쓰지 않는다 |

표의 세로축은 "로직이 있는가"와 "기능을 아는가"라는 **서로 다른 두 질문**이다. 이 두 질문을 따로 묻는 것이 챕터 전체를 관통하는 사고방식이다. 로직이 많다고 해서 기능을 아는 것은 아니며(뷰 컴포넌트), 기능 폴더에 산다고 해서 기능을 아는 것도 아니다(원칙 10).

## § 3.1 UI 원칙 8: 뷰 컴포넌트는 로직과/또는 바인딩을 가진다

저자는 Chapter 2에서 만든 뷰들이 무엇이었는지부터 다시 확인한다.

> **(p.48)** *"이전 챕터에서 우리는 '멍청한' 뷰를 전달했고, 그것을 **뷰 프리미티브**로 분류했습니다."*
>
> *"그렇게 해서 UI 라이브러리에 둘 수 있는 뷰들을 얻었습니다. 우리 기능도 쓸 수 있고, 다른 사람들도 쓸 수 있습니다."* (Figure 3.1)

> **(p.49)** *"이 책에서 **뷰 프리미티브**는 더 복잡한 뷰를 만드는 데 쓰이는 기본 빌딩 블록입니다. 버튼, 라벨, 스위치가 그 예입니다."*
>
> *"이 챕터에서는 뷰 프리미티브보다 한 단계 위로 논의를 끌어올려, 특정 뷰들을 **뷰 컴포넌트**라고 부를 것입니다. 뷰 컴포넌트는 데이터 바인딩을 이해하거나 로직을 캡슐화합니다. 그래서 우리는 그것을 '똑똑하다'고 부릅니다."*

용어에 대한 주의도 함께 붙는다.

> **(p.49) Note** — *"'컴포넌트'라는 용어는 유동적이고 플랫폼마다 다릅니다. 어떤 플랫폼에서는 뷰 컴포넌트가 작은 뷰를 뜻합니다. React Native 같은 플랫폼에서는 대부분의 뷰를 'Component'라고 부릅니다. 이 책에서는 데이터와 로직을 가진 것을 뷰 컴포넌트로 정의합니다."*

즉 이 책의 "컴포넌트"는 크기나 프레임워크의 용어가 아니라 **로직의 유무**로 정의된 개념이다. Compose에서 모든 `@Composable`을 흔히 "컴포넌트"라고 부르는 관행과도 다르므로, 이 문서에서는 책의 정의를 따른다.

그리고 저자는 Chapter 2에서 이미 컴포넌트를 하나 만들었다고 밝힌다.

> **(p.49)** *"사실 우리는 이전 챕터에서 이미 뷰 컴포넌트를 만들었습니다. `SelectionView`는 단순한 뷰 프리미티브가 **아닙니다**."*
>
> *"`SelectionView`는 요소 목록을 추적하고, 사용자가 어떤 요소를 토글하고 있는지 추적하며, 사용자가 액세서리 버튼을 탭하면 변경을 전파합니다."* (Figure 3.2)
>
> *"이 뷰는 효과적으로 작동하기 위해 상태와 로직과 데이터를 요구합니다. 그래서 단순한 버튼이나 라벨보다 정교합니다. 그래서 우리는 이것을 뷰 컴포넌트로 분류합니다."*

Chapter 2에서 `SelectionView`는 이름을 바로잡고(`TodoListView` → `SelectionView`) 제목과 리셋 버튼을 밖으로 밀어내는 과정을 거쳤다. 그렇게 단순해졌는데도 **목록 상태와 토글 로직은 여전히 뷰 안에 남는다.** 이 남은 로직이 `SelectionView`를 프리미티브와 구별해 준다.

### § 3.1.1 뷰 프리미티브와 뷰 컴포넌트 구별

> **(p.49)** *"`SelectionView`가 뷰 프리미티브보다 한 단계 위의 추상화 레이어에 있다는 점에 주목하세요. 뷰 컴포넌트는 뷰 프리미티브를 사용할 수 있지만, 그 반대는 안 됩니다."*

Figure 3.3은 이 층위를 그림으로 보여준다. UI Library 상자 안이 두 층으로 나뉜다. 위층 "View Components ('Smart', Contains logic)"에는 `SelectionView`와 점선 상자의 `SelectionElement`가 있고, 아래층 "View Primitives ('Dumb', Simple views)"에는 `ImageLabelView`, `SelectionItemView`, `TextButton`, `AccessoryButton`, `SubduedButton`, `Callout`이 나란히 있다. `SelectionView`는 아래층의 `SelectionItemView`를 쓰고, UI Library 바깥 Course domain의 `TodoItem`은 `SelectionElement` 쪽을 가리킨다. 이 마지막 화살표는 §3.2에서 다룬다.

컴포넌트의 예시는 대부분 OS가 이미 제공하는 것들이다.

> **(p.50)** *"뷰 컴포넌트의 예로는 내비게이션 바, 컬러 피커, 커스텀 맵 뷰, 날짜 스케줄러, 날짜 피커, 세그먼트 컨트롤, 키보드, 스테퍼, 슬라이더, 입력 필드, 텍스트 필드, 알림 표시 등이 있습니다."*
>
> *"OS가 컴포넌트를 제공하지만, 우리가 직접 컴포넌트를 만들어 보충해야 할 때가 많습니다."*
>
> *"뷰 컴포넌트는 더 많은 로직과 기능을 가집니다. 그러나 뷰 프리미티브와 마찬가지로, 자신이 쓰이는 기능을 **알지 못합니다**. 그래서 이론적으로는 수백 개의 기능에 쓸 수 있습니다."*
>
> *"컴포넌트는 고객 대면 기능을 알지 못하므로, 재사용 가능한 뷰의 UI 라이브러리에도 살 수 있습니다."*

날짜 피커를 떠올리면 이해가 쉽다. 달력 계산, 선택 범위 검증, 스크롤 상태 등 로직은 매우 많지만, 그 날짜가 수업 예약에 쓰이는지 생일 입력에 쓰이는지는 전혀 모른다. **"똑똑함"과 "기능을 앎"은 별개의 축이다.**

이 분류가 실제 폴더 구조를 강제하지는 않는다.

> **(p.50)** *"이 뷰들을 별도의 폴더에 넣지는 않는다는 점에 주목하세요. 그렇게 할 수도 있지만, 지금 다룰 뷰가 한 줌뿐이기 때문입니다. 대신 더 잘 추론하기 위해 **머릿속으로** 분류합니다."*

그렇다면 왜 굳이 분류하는가에 대한 답이 이어진다.

> **(p.50)** *"그러나 이 분류에는 이유가 있습니다. 여러 컴포넌트, 기능, 화면, 디자인 시스템을 다루다 보면 '이 뷰는 어디에 속하는가?', '이 뷰는 내 기능의 일부인가?', '이 뷰는 내 데이터 모델에 어떻게 연결되는가?' 같은 질문에 답하기 어렵습니다."*
>
> **(p.51)** *"뷰의 역할이 불분명하면 뷰와 특정 기능 사이에 강한 연결이 생길 수 있습니다. 그러면 UI 라이브러리를 만들기 어려워질 뿐 아니라, 코드를 별도의 기능이나 별도의 모듈로 옮기는 일도 복잡해집니다."*

분류의 목적은 명명법을 늘리는 데 있지 않다. **모듈을 나눌 때 어느 뷰가 어느 쪽으로 가야 하는지를 미리 판단할 수 있게 해 주는 데 있다.** 이 관점은 Scale 권의 모듈화 챕터로 그대로 이어진다.

## § 3.2 UI 원칙 9: 뷰 컴포넌트는 비즈니스 로직을 모른다

`SelectionView`를 컴포넌트로 분류하면 곧바로 과제가 생긴다. 이 뷰는 문자열 몇 개를 받고 끝나는 뷰가 아니다.

> **(p.51)** *"`SelectionView`를 뷰 컴포넌트로 분류했으므로, 그 안에서 어느 정도 로직을 다뤄야 한다는 뜻입니다."*
>
> *"라벨 같은 뷰 프리미티브처럼 문자열 몇 개를 넘기고 끝낼 수 없습니다."*
>
> *"우리는 **양방향 바인딩**을 다루고 있습니다. `Course`가 `SelectionView`에 데이터를 넘겨 todo 항목을 보여줄 뿐 아니라, 사용자가 todo 항목을 탭하면 `SelectionView`의 상태가 바뀌고 그 변경이 `Course` 모델을 업데이트해야 합니다."*

여기서 긴장이 생긴다. `Course` 기능의 데이터를 다뤄야 하는데, `Course` 기능을 알아서는 안 된다.

> **(p.51)** *"`CourseView`처럼 이 뷰도 로직과 데이터를 가집니다. 그러나 `CourseView`와 **달리** `Course` 기능에 대해 **모릅니다**. 그런데도 우리는 이 컴포넌트에서 `Course` 기능의 데이터를 쓰고 싶습니다."*
>
> *"`SelectionView`가 코스를 알게 만들 위험이 있습니다. `SelectionView`를 뷰 컴포넌트로 분류했으므로, 그것이 비즈니스 로직을 알거나 '신경 쓰는' 것을 원하지 않습니다. 사실 이 컴포넌트를 별도의 UI 라이브러리로 옮김으로써 이 점을 명시적으로 만들었습니다."*

해법은 단순하다.

> **(p.51)** *"다행히 간단한 해결책이 있습니다."*
>
> *"우리 경우에는 인터페이스(Swift 용어로는 프로토콜)를 도입하고, `SelectionElement`라고 부른 뒤, `TodoItem`이 그것을 따르게(conform) 할 수 있습니다. 이제 `SelectionView`는 `Course` 기능을 모르면서도 `TodoItem` 타입과 함께 작동할 수 있습니다."* (Figure 3.4)

Figure 3.3과 3.4에서 `SelectionElement`가 **UI Library 쪽**에 있다는 점이 중요하다. 인터페이스를 소유하는 쪽이 UI 라이브러리이고, 도메인의 `TodoItem`이 그 인터페이스에 맞춰 들어온다. 의존 화살표는 `TodoItem` → `SelectionElement`로, 기능 쪽에서 라이브러리 쪽을 향한다. 라이브러리는 기능 쪽으로 향하는 화살표를 하나도 갖지 않는다.

> **(p.52)** *"이렇게 하면 `SelectionView`가 기능을 알지 못하도록 보장할 수 있습니다. 그래도 바인딩은 여전히 해결해야 합니다. 사용자가 요소를 탭해 `TodoItem`을 완료하거나 취소하면, `Course` 모델이 최신 상태를 반영하도록 업데이트되어야 합니다."*
>
> *"클로저나 SwiftUI의 `@Binding` 키워드 같은 여러 기법을 쓸 수 있습니다. 다음 챕터에서 코드 수준으로 살펴볼 것입니다."*

> **읽을 때 주의할 지점** — 양방향 바인딩의 두 방향은 **서로 다른 도구로 끊는다.** 데이터가 도메인에서 뷰로 내려오는 방향은 인터페이스(`SelectionElement`)가 끊는다. 뷰는 `TodoItem`이라는 구체 타입 대신 "선택 가능한 무언가"라는 추상만 본다. 반대로 변경이 뷰에서 도메인으로 올라가는 방향은 클로저나 `@Binding`이 끊는다. 뷰는 "누가 이 변경을 받는가"를 모른 채 콜백을 호출할 뿐이다. §3.11의 원칙 9 요약이 "인터페이스**나 클로저**"라고 두 도구를 나란히 적은 이유가 여기에 있다. 한쪽 방향만 끊으면 다른 방향으로 결합이 새어 들어온다.

## § 3.3 재사용 가능한 컴포넌트는 가치가 있는가?

원칙 9를 세운 직후, 저자는 스스로 반론을 제기한다.

> **(p.52)** *"우리는 `SelectionView`를 재사용 가능하게 만들었지만, 그것이 가치 있는지는 어떻게 판단할까요? 이 질문은 우리의 설계 접근에 대한 중요한 질문으로 이어집니다."*
>
> *"`SelectionView`가 UI 라이브러리에 살 수 있도록 재사용 가능하게 만드는 데 추가 노력을 들이고 있다는 점에 주목하세요."*
>
> *"어떤 사람들은 이것을 과잉 설계라고 말할 수 있습니다. 이것을 요구하는 기능은 `Course` **하나뿐**이기 때문입니다. 대안으로 `TodoItem` 타입을 사용하는 `TodoListView`를 만드는 편이 더 쉽습니다. 그러면 **오직** `CourseView`만 그것을 쓸 수 있고, 일을 진행하기에는 그것으로 충분합니다."*

Figure 3.5는 그 대안의 모습이다.

> **(p.53)** *"`TodoListView`는 Course UI에 살며 UI 라이브러리와 연결되어 있지 않습니다."*
>
> *"`TodoListView`는 `Course` 모델의 일부인 `TodoItem`을 직접 사용합니다."* (Figure 3.5)

> **(p.53) Note** — *"이것이 **대안** 해법이라는 점을 강조하고 싶습니다. 책 전반에서는 `SelectionView`를 사용할 것입니다."*

대안을 택했을 때 무엇이 바뀌는지가 정확히 서술된다.

> **(p.53)** *"뷰 컴포넌트가 계층에서 위로 도약했습니다. `SelectionView`는 UI 라이브러리에 살던 것에서, **오직** `Course` 도메인만 쓰는 `TodoListView`가 되었고, **게다가** 이제 비즈니스 로직까지 포함합니다."*
>
> *"한편으로는 `TodoListView`가 `TodoItem` 인스턴스를 직접 다룰 수 있으므로 코드가 더 단순합니다. 다른 한편으로는 **많은** 다재다능함을 포기했습니다."*

"위로 도약했다"는 표현은 §3.1.1의 층위 그림을 전제로 한다. 인터페이스 하나를 빼면 뷰는 컴포넌트 층에서 기능 뷰 층으로 올라가고, 거처도 UI 라이브러리에서 기능 도메인으로 옮겨진다. **뷰의 분류는 뷰 자체의 코드보다 그 뷰가 무엇에 의존하는가로 결정된다**는 점이 여기서 처음 드러난다.

## § 3.4 언제 재사용 가능하게 만들 것인가

대부분의 개발자가 떠올리는 판단 기준은 재사용 확률이다. 저자는 그 기준을 먼저 꺼낸 뒤 바로 한계를 짚는다.

> **(p.54)** *"때로는 **재사용 확률**을 따지고 싶을 수 있습니다. '다른 기능도 이 컴포넌트가 필요할까?'라고 자문하는 식으로요."*
>
> *"우리는 **확률**의 관점에서 생각할 것입니다. 그러나 안타깝게도 우리는 미래를 잘 예측하지 못합니다. 예측할 수 있다면 모든 소프트웨어 프로젝트가 쉽게 끝났을 것입니다."*

그래서 경험 법칙은 보수적이다.

> **(p.54)** *"**경험 법칙: 가설적 시나리오를 위해 컴포넌트를 재사용 가능하게 만들지 않는 쪽에 걸어라. 컴포넌트가 재사용 가능해야 한다면, 필요해졌을 때 재사용 가능하게 만들어라.**"*

그런데 이 법칙에는 곧바로 단서가 붙는다. 이 책 자신이 그 법칙을 어겨 왔기 때문이다.

> **(p.54)** *"그렇다고 미리 재사용 가능한 컴포넌트를 **절대** 만들지 말라는 뜻은 아닙니다."*
>
> *"더 많은 미묘함이 있습니다. 사실 이 책에서 우리는 일반적인 조언을 거슬러 미리 재사용 가능한 뷰를 만들어 왔습니다."*
>
> *"목표는 위험을 최소화하는 것입니다. 재사용 가능한 컴포넌트를 만들었는데 다른 기능이 그것을 필요로 하지 않더라도 **피해가 거의 없도록** 하는 것입니다."*

### § 3.4.1 재사용 가능한 컴포넌트를 만들기 위한 휴리스틱

저자는 실패 시나리오 두 가지와 성공 시나리오 하나를 대비시킨다.

> **(p.54)** *"이 뷰를 매우 재사용 가능하게 만들려고 상당한 노력을 들였다고 해 봅시다. 나중에 다른 기능이 이 컴포넌트를 **요구하지 않는다**는 것을 알게 되면, 무거운 사전 투자는 시간을 낭비한 셈입니다."*
>
> *"마찬가지로, 재사용 가능하게 만드는 데 시간은 최소한으로 썼지만 그 때문에 컴포넌트가 상당히 복잡해진 상황을 상상해 봅시다. 시간이 흘러 다른 기능이 실제로는 이 컴포넌트를 필요로 하지 않는다는 것을 알게 됩니다. 이제 이유 없이 복잡한 컴포넌트를 떠안아야 합니다."*
>
> *"반대로, 재사용 가능하게 만드는 데 **매우 적은** 시간과 노력이 들고 **복잡도가 낮게 유지된다면**, 그 투자는 할 만한 가치가 있을 수 있습니다. 위험을 낮게 유지하기 때문입니다."*

Figure 3.6은 이 판단을 2차원 평면으로 그린다. 제목은 *"단일 사용 사례를 위해 컴포넌트를 재사용 가능하게 만들어야 하는가?"*이다. 세로축은 **시간 투자**, 가로축은 **증가하는 복잡도**다. 원점 근처의 작은 사각형만 "Yes"이고, 그것을 둘러싼 중간 영역은 "No", 나머지 넓은 영역은 "Definitely not"이다. 두 축 중 하나만 커져도 "Yes" 영역을 벗어난다는 점이 이 그림의 핵심이다. "Yes" 칸이 그림에서 가장 작은 영역이라는 점도 저자의 기본값이 "만들지 않는다"임을 보여준다.

이 틀을 `SelectionView`에 적용하는 과정에서 저자는 스스로 확률 논법을 경계한다.

> **(p.55)** *"우리 경우, `SelectionView`가 다른 무언가에 쓰일 가능성이 높다고 예측합니다. 그러나 그것은 함정입니다. 우리는 점쟁이가 아니기 때문입니다. 선택 UI가 사용자 인터페이스에서 매우 흔하더라도 여전히 잘못 예측할 수 있습니다."*
>
> *"대신 투자를 따져 봅시다. 작은 인터페이스를 도입하고 **기능 뷰**를 UI 라이브러리용 **뷰 컴포넌트**로 바꿔야 합니다. 추가 작업은 거의 없습니다. 속성 두세 개짜리 프로토콜 하나를 추가할 뿐이고, 뷰의 핵심 구현은 바뀌지 않습니다. 시간 투자는 작고 복잡도는 낮게 유지되지만, 잠재적 보상은 큽니다."*
>
> *"투자가 적고 복잡도가 낮게 유지되므로, 처음부터 `SelectionView`를 재사용 가능하게 만드는 것은 감수할 만한 위험이라고 말할 수 있습니다."*

그리고 이 휴리스틱이 Chapter 2의 결정을 소급해서 설명한다.

> **(p.55)** *"이것이 이전 챕터에서 우리가 뷰를 곧바로 UI 라이브러리에 둔 이유를 설명합니다. **거의 0에 가까운** 추가 노력으로 그 뷰들은 즉시 재사용 가능해졌습니다. 필요한 것은 이름을 바꾸는 일뿐이었습니다. 우리는 가설적 시나리오를 위해 미리 복잡도를 올린 적이 없습니다."*

> **읽을 때 주의할 지점** — 이 절은 "재사용될 것 같으면 재사용 가능하게 만들라"는 말이 아니다. 저자는 `SelectionView`가 재사용될 가능성이 높다는 예측을 **근거로 쓰지 않겠다고 명시적으로 거부한다.** 판단의 근거는 오직 "틀렸을 때 잃는 것"이다. 확률은 추정할 수 없지만, 투자와 복잡도는 지금 이 자리에서 측정할 수 있다. 그래서 이 휴리스틱은 불확실성을 예측하는 도구가 아니라 **불확실성을 무시해도 되는 영역을 찾는 도구**다. Chapter 2가 원칙 7에서 "가설적 시나리오를 위해 만들지 마라"고 했던 것과 이 절은 충돌하지 않는다. 가설적 시나리오를 위해 **복잡도를 올리지 말라**는 것이고, 복잡도를 올리지 않는 재사용성은 공짜에 가깝다는 것이다.

## § 3.5 UI 원칙 10: 기능은 로컬 컴포넌트를 가질 수 있다

모든 뷰가 UI 라이브러리로 가는 것은 아니다. 다음 대상은 Chapter 2에서 이미 "기능 근처에 둔다"고 결정한 `ScheduleView`다.

> **(p.56)** *"다른 뷰를 봅시다. `ScheduleView`는 학생이 강사와의 1:1 통화 일시를 확인할 수 있게 하는 작은 뷰입니다."* (Figure 3.7)
>
> *"로직을 거의 또는 전혀 담지 않으므로 이것을 **뷰 프리미티브**로 간주합니다. 버튼을 위한 콜백 두 개와 라벨 몇 개만 있으면 됩니다."*
>
> *"다른 뷰 프리미티브와 **달리**, 우리는 `ScheduleView`를 `Course` 기능 안의 폴더에 두기로 합니다. `ScheduleView`가 `Course` 기능의 구체적인 사정에 강하게 묶여 있기 때문입니다."* (Figure 3.8)

거처를 정하는 근거는 여전히 예측이다. 저자는 그것이 예측일 뿐이라는 점을 숨기지 않는다.

> **(p.57)** *"다른 기능이 이 뷰를 요구할 **가능성이 낮으므로** `Course` 도메인 가까이에 둡니다. 반면 우리가 UI 라이브러리에 둔 뷰 프리미티브는 다른 기능이 사용할 **가능성이 높습니다**."*
>
> *"그러나 이것은 여전히 예측입니다."*

그래서 예측이 틀렸을 때를 대비하는 장치가 원칙 10의 본체다.

> **(p.57)** *"유연성을 유지하기 위해, 다른 뷰들처럼 `ScheduleView`도 자신이 쓰이는 `Course` 기능을 **모르는 상태**로 유지합니다."*
>
> *"우리가 틀렸고, 나중에 다른 화면에서 이 뷰가 필요해졌다고 해 봅시다. 그러면 UI 라이브러리로 옮기는 일은 간단합니다. 코스에 대한 어떤 지식과도 완전히 분리된 자율적인 뷰로 설계했기 때문입니다."*
>
> *"결과적으로 우리는 `ScheduleView`를 `Course` 기능 폴더 안에 두면서도 그 독립성을 유지합니다."*

§3.4의 휴리스틱이 여기서도 작동한다. `ScheduleView`를 UI 라이브러리에 두지 않는 결정은 "재사용될 것 같지 않다"는 예측에 기댄다. 하지만 그 예측이 틀려도 비용이 거의 없도록, **이동 비용을 0에 가깝게 만들어 두는 것**이 원칙 10의 요구다. 거처는 예측으로 정하되, 그 예측의 실패 비용은 설계로 없앤다.

> **읽을 때 주의할 지점** — Chapter 2의 §2.6.1은 `CourseView`와 `ScheduleView`를 함께 "기능별 뷰(Course 도메인)"로 묶었다. 이 챕터는 그 둘을 **서로 다른 분류로 갈라 놓는다.** `CourseView`는 비즈니스 로직을 아는 **기능 뷰**이고, `ScheduleView`는 기능 폴더에 살 뿐 아무것도 모르는 **뷰 프리미티브**다. Figure 3.10과 3.17도 `ScheduleView`를 Course UI 안의 "View Primitives ('Dumb', Specific to a feature)" 상자에 넣어 이 구분을 표시한다. 즉 Chapter 2의 "기능별"은 **거처**를 말한 것이고, Chapter 3의 "기능 뷰"는 **앎**을 말한 것이다. 이름이 비슷해서 같은 개념으로 읽기 쉽지만, 원칙 10은 정확히 이 두 축이 서로 독립적이라고 말하는 원칙이다. 정리하면 `ScheduleView` 하나에 세 축이 모두 걸려 있다. 이름은 구체적이고(Ch2 §2.5.1), 거처는 기능 폴더이며(원칙 10), 앎은 없다(원칙 10).

## § 3.6 UI 원칙 11: 기능 뷰는 비즈니스 로직에 연결된다

세 번째 분류가 여기서 도입된다.

> **(p.57)** *"뷰 프리미티브와 뷰 컴포넌트 외에도, 비즈니스 로직과 함께 기능을 지탱하는 뷰가 있습니다. 그래서 우리는 기능에 특화된 뷰를 **기능 뷰**로 분류합니다."*
>
> *"예를 들어, 우리 앱의 다른 뷰들보다 더 높은 추상화 수준에 있는 선언형 뷰 `CourseView`를 생각해 봅시다. 이 뷰는 원래 브리핑의 Course 화면을 나타냅니다."* (Figure 3.9)

절 자체는 짧다. 정의만 세우고, 그 정의가 실제로 무엇을 뜻하는지는 다음 두 절(§3.7, §3.8)에서 풀어 간다.

## § 3.7 뷰를 데이터에 연결하기

> **(p.58)** *"`CourseView` 같은 고객 대면 기능은 자신이 쓰는 뷰들뿐 아니라, 명시적이든 암묵적이든 관련된 비즈니스 로직도 압니다."*
>
> *"그래서 우리는 이것을 **기능 뷰**로 분류합니다. UI와 비즈니스 로직이 연결되는 곳입니다."*

곧바로 예상되는 질문에 대한 짧은 답이 붙는다.

> **(p.58) Note** — *"왜 `CourseView`를 '화면'이 아니라 '기능 뷰'라고 부르는지 궁금할 수 있습니다. 다음 절에서 다루겠지만, 짧게 답하면 이렇습니다. 화면은 기능 뷰, 뷰 프리미티브, 뷰 컴포넌트 등 여러 가지가 될 수 있고, 항상 비즈니스 로직을 아는 것도 아닙니다. 둘째로, '기능 뷰'가 항상 화면 전체를 쓰는 것도 아닙니다."*

그리고 처음으로 UI 레이어와 모델 레이어를 한 그림에 함께 그린다.

> **(p.58)** *"더 온전한 맥락을 보여드리겠습니다. 이번에는 UI 레이어에 **더해** 모델 레이어까지 보여드립니다."*

> **(p.58) Note** — *"그래프를 작게 유지하기 위해 `Networking` 같은 다른 모델 도메인은 생략합니다."*

Figure 3.10의 구조는 다음과 같다. 왼쪽의 Course domain 상자 안에 Course UI와 Course models & logic이 위아래로 있다. Course UI 안에는 "Feature Views (Connects UI to business logic)" 상자의 `CourseView`와, 그 아래 "View Primitives ('Dumb', Specific to a feature)" 상자의 `ScheduleView`가 있다. Course models & logic 안에는 `Marketplace`, `CourseService`, `Course Model`, 그리고 `TutorAPI`·`Calendar`·`TodoAPI`가 있다. 오른쪽의 UI Library에는 컴포넌트 층의 `SelectionView`와 프리미티브 층의 여섯 뷰가 있다. `CourseView`에서는 UI Library의 거의 모든 뷰로 화살표가 뻗어 나가고, 동시에 `Course Model`로 향하는 굵은 화살표 하나가 있다. **UI Library에서 모델 레이어로 향하는 화살표는 하나도 없다.** 그 굵은 화살표 하나가 기능 뷰를 기능 뷰로 만든다.

> **(p.58)** *"이 예에서 `CourseView` 기능이 `Course` 모델을 **안다**는 점에 주목하세요. 즉 `CourseView`는 지금까지 도입한 **어떤** 뷰보다 구체적인 뷰입니다. 우리는 `CourseView`를 재사용성이 높은 뷰로 보지 않습니다. Course 기능 안에서만 쓸 수 있기 때문입니다."*
>
> *"`CourseView`가 `CourseService`에서 `Course`를 **어떻게** 받아올지는 아직 정하지 않았습니다. 하지만 먼저, `CourseView`가 `Course` 모델을 자신의 뷰와 하위 뷰들에 연결, 즉 **바인딩**함으로써 작동한다는 것을 아는 것이 중요합니다."*
>
> **(p.59)** *"`CourseView`가 작동하려면 `Course` 모델의 인스턴스가 필요합니다."*
>
> *"뷰를 비즈니스 로직에 연결하는 방법은 여러 가지가 있습니다. 몇 가지 대안을 살펴봅시다."*

## § 3.8 바인딩은 여러 형태로 온다

저자는 이 절이 논쟁의 한복판이라는 점을 먼저 인정한다.

> **(p.59)** *"`CourseView`를 `Course` 모델에 연결하는 방법은 셀 수 없이 많습니다. 뷰모델, 컨트롤러, 선언형 바인딩, 상태 핸들러, 클로저, 퍼블리셔, 코디네이터 등이 있습니다."*
>
> *"UI를 데이터에 연결하는 방법을 고르는 순간, 우리는 UI 프레임워크와 아키텍처, 그리고 어떤 패턴이 '최고'인가에 대한 말다툼의 수문을 엽니다."*
>
> *"모바일 개발자들과 셀 수 없이 토론해 본 제 경험으로는, UI 아키텍처 논쟁의 상당 부분이 대체로 '바인딩'이라는 개념에 집중된다고 말해도 무방합니다. 저마다 규칙과 모범 사례와 장단점이 있습니다."*
>
> *"모바일 개발자로서 우리는 지금 쓰는 아키텍처가 완벽하게 적절할 때조차 다른 UI 아키텍처로 옮겨 가느라 스스로를 바쁘게 만드는 경향이 있습니다."*

마지막 문장이 Chapter 1의 문제의식과 곧바로 이어진다. Chapter 1은 "어떤 UI 아키텍처를 쓸 것인가"라는 질문 자체를 덜 중요하게 만들려 했고, 이 절은 그 논쟁의 대부분이 바인딩이라는 좁은 지점에 몰려 있다고 진단한다. 그래서 이 절에서도 특정 패턴을 옹호하지 않고, **"이 추상화가 제 몫을 하는가"**라는 하나의 질문으로 여러 패턴을 평가한다.

### § 3.8.1 고전적 뷰모델

> **(p.59)** *"흔한 접근은 뷰를 모델 레이어에서 떼어 놓기 위해 뷰모델을 구현하는 것입니다."*
>
> *"뷰모델로 설계한다면, `CourseView`가 의존하는 새 `CourseViewModel`을 도입할 것입니다. 그다음 `CourseViewModel`이 `Course`에, 그리고 필요하면 `CourseService`에도 직접 연결됩니다."*
>
> *"아이디어는 `CourseView`의 로직을 `CourseViewModel`로 추출하는 것입니다. 그러면 더 많은 비즈니스 로직이 `CourseView` 밖에 머물고, `CourseViewModel`은 단위 테스트가 가능해집니다."* (Figure 3.11)

그런데 그림을 보면 중요한 사실이 하나 드러난다.

> **(p.60)** *"그래프를 보면 `CourseView`에서 `Course` 모델로 가는 경로가 **여전히** 있습니다. 그 사이에 `CourseViewModel`이라는 홉(hop)이 하나 더 끼었을 뿐입니다."*
>
> *"그래서 우리는 `CourseView`를 여전히 **기능 뷰**로 볼 수 있습니다. 비즈니스 로직과 아무 연결이 없는 다른 뷰들과 달리, `CourseView`는 **여전히** 비즈니스 로직에 의존합니다. 다만 이제 `Course` 모델에 직접이 아니라 **간접적으로** 의존할 뿐입니다."*

기능 뷰의 판정 기준이 여기서 분명해진다. 모델에 **직접** 닿는지가 아니라, 모델까지 **경로가 있는지**가 기준이다.

### § 3.8.2 관심사 분리 — 그러나 그 가치는?

뷰모델의 장점은 분명하다.

> **(p.60)** *"뷰모델이 자리 잡으면 `CourseView`는 모델 레이어로부터 한 단계 **분리**됩니다. `CourseView`와 `Course` 모델 사이의 강한 결합이 사라집니다."*
>
> *"이 분리는 유연성을 줍니다. `CourseView`를 고치지 않고도 `CourseViewModel`의 구현을 바꿀 수 있습니다. 예를 들어 테스트를 위해 `CourseViewModel`이 `CourseView` 모르게 하드코딩된 `Course` 인스턴스를 돌려줄 수 있습니다."*

그러나 이 사례에서는 얻는 것이 거의 없다고 판정한다.

> **(p.60)** *"그러나 우리의 구체적인 사례에 이 해법을 대 보면, `CourseViewModel`을 도입해서 **얻는 것이 거의 없습니다**."*
>
> *"앞서 말했듯 우리는 `CourseView`를 재사용성이 높은 뷰로 보지 않습니다. 그리고 대부분의 로직과 복잡성을 모델 레이어로 밀어내고, 재사용 가능한 뷰를 추출해 UI 라이브러리에 두는 데 이미 **많은** 노력을 들였습니다. 그 덕분에 `CourseView`는 가볍고, 비즈니스 로직 코드는 대부분 단위 테스트가 가능합니다."*
>
> **(p.61)** *"`CourseViewModel`을 도입하더라도 그것 역시 매우 가벼울 것입니다. 그래서 `CourseViewModel`은 매우 얕은 추상화로 볼 수 있습니다. 가치는 거의 더하지 않으면서, 간접 레이어를 하나 더 추가해 코드를 복잡하게 만듭니다."*
>
> *"이 시나리오에서는 그 트레이드오프가 가치가 없으므로, 빼는 편이 낫습니다."*

그리고 선언형 세계에서는 관점이 조금 달라진다는 점도 짚는다.

> **(p.61)** *"선언형 프로그래밍 세계에서는, 별도의 `CourseViewModel` 없이도 `CourseView` 자체를 뷰모델로 보는 사람도 있을 수 있습니다. 비즈니스 로직을 사용자 인터페이스에 연결하기 때문입니다."*

`CourseViewModel`이 얕아지는 이유는 뷰모델이라는 패턴에 있지 않다. **Book 0부터 Chapter 2까지 쌓은 선행 작업 때문이다.** 비즈니스 로직은 이미 두꺼운 모델 레이어(`CourseService`, `Course`)로 갔고, 표시 로직은 이미 UI 라이브러리의 뷰로 갔다. 그 사이에 남은 것이 거의 없으니 뷰모델이 할 일도 거의 없다. 그래서 이 판정은 "뷰모델은 나쁘다"로 일반화할 수 없다. 앞의 설계가 뷰모델의 일을 미리 가져가 버렸다는 뜻이다.

### § 3.8.3 간접 레이어가 더 필요한지 판단하기

일반 원칙은 한 문장으로 정리된다.

> **(p.61)** *"일반적인 가이드라인으로, 뷰모델 같은 간접 레이어는 **그것이 만드는 문제보다 더 많은 문제를 해결할 때** 도입을 고려하세요."*
>
> *"뷰모델이 무거운 일을 **많이** 한다면 도입할 정당성이 있습니다. 새 레이어를 도입하고, 뷰는 그 레이어를 거쳐 **간접적으로** 비즈니스 모델에 의존하게 됩니다."* (Figure 3.12)
>
> *"그러나 우리 경우 `CourseViewModel`은 최소한의 일만 할 것입니다. 이 레이어는 가치는 거의 주지 않으면서 복잡성과 간접성만 더합니다."* (Figure 3.13)
>
> **(p.62)** *"그래서 `CourseView`는 뷰모델 없이 계속 진행합니다."*

Figure 3.12와 3.13은 같은 구조의 두 변형이다. 뷰모델이 두꺼우면 추상화가 정당화되고, 얇으면 복잡도만 늘어난다. 이 기준은 Book 0의 Chapter 7이 "간접층에는 값이 붙는다"고 정리했던 것과 같은 판단 축이다. 거기서는 테스트와 의존성만을 위해 인터페이스를 늘리면 코드가 이해하기 어려워진다고 경고했고, 여기서는 할 일 없는 뷰모델이 같은 비용을 치르게 한다고 경고한다.

### § 3.8.4 뷰모델이 말이 되는 경우

저자는 뷰모델을 배척하지 않는다. 네 가지 정당한 경우를 든다.

> **(p.62)** *"뷰모델이나 그와 비슷한 타입을 도입할 좋은 이유들이 있습니다. 재사용 가능한 뷰에 뷰모델을 연결하는 경우입니다. 그러면 뷰가 비즈니스 로직으로부터 완전히 분리된 상태를 유지할 수 있습니다."*
>
> *"큰 뷰를 더 작게 유지하는 데 도움이 되는 경우도 있습니다."*
>
> *"또는 어떤 플랫폼은 뷰모델을 더 요구합니다. Android에서는 뷰모델이 기본 선택일 수 있습니다. 라이프사이클을 인지하고, 화면 회전 같은 구성 변경 중에도 상태를 보존하기 때문입니다."*
>
> *"뷰모델에 손을 뻗을 또 다른 이유는, 비즈니스 로직의 데이터가 특정 화면이나 UI에서 쓰기에 인체공학적이지 않을 때입니다."*

| 정당한 경우 | 뷰모델이 해결하는 문제 |
|---|---|
| 재사용 가능한 뷰에 연결할 때 | 뷰를 비즈니스 로직으로부터 완전히 분리한다 |
| 뷰가 클 때 | 뷰의 크기를 줄인다 |
| 플랫폼이 요구할 때 (Android) | 라이프사이클 인지, 구성 변경 중 상태 보존 |
| 데이터가 UI에 맞지 않을 때 | 데이터 변환을 맡는다 |

마지막 경우는 구체적인 시나리오로 설명된다.

> **(p.62)** *"예를 들어 깔끔한 `Course` 모델과 `CourseService`가 없다고 상상해 봅시다. 대신 데이터를 공급하는 서드파티 Education SDK에 의존합니다. 이 SDK는 코스에 대해 **아무것도** 모릅니다."*
>
> *"그 경우 SDK를 `CourseView`에 연결하려면 데이터를 변환해 UI가 소비하기 쉽게 만드는 코드 조각이 필요합니다."*
>
> *"`CourseViewModel`이 복잡한 데이터 변환을 맡아서, `CourseView`가 가볍고 서드파티 솔루션을 모르는 상태로 남도록 보장할 수 있습니다. 이 접근은 비즈니스 로직과 UI 사이의 명확한 분리를 유지하는 데 도움이 됩니다."* (Figure 3.14)
>
> **(p.63)** *"이것은 `CourseView`에 특화된 맞춤형 해법이 될 것입니다. 더 일반적인 해법이 필요하다면, 그 코드를 뷰모델 밖, 모델 레이어로 밀어내 여러 사용 사례를 지원할 수 있습니다."*

> **(p.63) Note** — *"더 자세한 내용은 'UI Frameworks, Architectures, and Supporting Multiple Products' 챕터를 참고하세요."*

이 Note가 가리키는 곳은 Chapter 1의 §1.4.3 어댑터 패턴이다. 뷰모델이 데이터 변환을 맡는 경우, 그것은 사실상 **화면 하나에만 쓰이는 어댑터**다. 그리고 그 변환이 여러 곳에서 필요해지면 어댑터를 모델 레이어로 내려보낸다. 뷰모델과 어댑터는 이름만 다를 뿐, "UI가 원하는 모양"과 "도메인이 가진 모양" 사이를 번역한다는 같은 역할을 한다.

### § 3.8.5 명령형 코드에서 고려할 점

선언형 뷰에서는 뷰모델을 빼도 괜찮았지만, 명령형 코드에서는 사정이 다르다.

> **(p.63)** *"개발자들이 뷰모델이나 비슷한 패턴에 의존하는 또 다른 이유는, 명령형 코드 같은 특정 시나리오에서 뷰 관련 코드가 거대해질 수 있기 때문입니다."*
>
> *"iOS에서는 UIKit의 뷰 컨트롤러를 통해 뷰를 데이터에 바인딩하는 경우가 많습니다. 뷰 컨트롤러는 뷰를 담고, **동시에** 라이프사이클을 인지합니다. 예를 들어 기기 회전이나 글꼴 크기 변경을 감지하고, 앱이 백그라운드나 포그라운드로 전환되는 시점을 감지합니다. 뷰 컨트롤러는 뷰의 중심점, 즉 '화면'이므로, 개발자들은 비즈니스 로직을 뷰 컨트롤러에 두는 경향이 있습니다."*
>
> *"라이프사이클 인지, 뷰를 설정한다는 사실, 비즈니스 로직과의 직간접적 연결 때문에 뷰 컨트롤러는 꽤 크고 복잡해지는 경향이 있습니다. 신중하게 관리하지 않으면 때로는 수천 줄에 이릅니다."*
>
> **(p.64)** *"그래서 개발자들은 뷰 컨트롤러에서 **모든** 비즈니스 로직을 빼내 줄 수와 복잡성을 줄이려고 합니다. 그리고 다시 뷰모델이나 다른 패턴 같은 다양한 중개자로 바인딩을 처리합니다."* (Figure 3.15)
>
> *"뷰 컨트롤러에서 비즈니스 로직을 빼내는 것은 복잡성과 크기를 통제하는 한 가지 접근입니다."*
>
> *"그러나 뷰모델 말고도, **뷰** 관련 코드의 대부분을 추출해서 뷰 컨트롤러를 가볍게 만드는 방법이 있습니다."*

거대한 뷰 컨트롤러(흔히 "Massive View Controller")에 대한 표준적인 처방은 비즈니스 로직을 **빼내는** 것이다. 저자는 그 반대편, 즉 **뷰를 빼내는** 쪽을 제안한다.

### § 3.8.6 명령형 코드를 더 가볍게

> **(p.64)** *"앞서 쓴 원칙을 그대로 써서 뷰 컨트롤러를 꽤 가볍게 만들 수 있습니다. 바로 **기능 뷰**와 **뷰 컴포넌트**를 구별하는 것입니다. 그 결과 뷰모델이 필요 없어지고, 간접 레이어가 하나 줄어 코드가 더 단순해집니다."*
>
> **(p.65)** *"약간 다른 사고방식으로 이를 달성할 수 있습니다. 보통 뷰 컨트롤러는 뷰를 설정하는 데 많은 무거운 일을 합니다. 하지만 **반드시** 그래야 한다는 법은 없습니다. 그렇게 하라고 강요하는 성가신 팀 리더가 있지 않다면요."*
>
> *"조금만 노력하면 별도의 뷰를 만들고 뷰 컨트롤러가 그것에 의존하게 할 수 있습니다. 즉 뷰 컨트롤러를 작게 유지하려고 타입과 패턴을 더 **추가하는** 대신, 뷰를 **빼내기만** 하면 됩니다."*
>
> *"iOS에서는 뷰를 별도 파일로 추출해 뷰 컨트롤러에 제공할 수 있습니다. 그러면 뷰 컨트롤러는 뷰를 설정할 책임을 지는 대신 뷰에 **의존**하게 됩니다."*
>
> *"이제 뷰 컨트롤러는 뷰 라이프사이클만 신경 쓰면 됩니다. 무언가 바뀌면 뷰 컨트롤러가 자신의 뷰를 업데이트할 수 있습니다."*

뷰모델이 필요 없어지는 이유도 앞 절과 같다. 비즈니스 로직이 이미 두껍기 때문이다.

> **(p.65)** *"다음으로, 우리는 비즈니스 로직을 UI 레이어 **밖으로 밀어내는** 데 **많이** 집중했기 때문에 비즈니스 로직이 꽤 '두껍습니다'."*
>
> *"그러니 이 UI 레이어에는 비즈니스 로직이 거의 필요 없습니다. 따라서 뷰 컨트롤러가 비즈니스 로직에 직접 의존하게 하고, 뷰 컨트롤러가 모델을 UI에 바인딩하게 할 수 있습니다."*

Figure 3.16은 이 "가벼운 접근(Lean approach)"을 세 상자로 그린다. 가운데 Viewcontroller(안에 Lifecycle)가 있고, 왼쪽의 View에 의존하며, 오른쪽의 Business logic에는 "Direct dependency (No patterns such as MVVM, MVP, etc)"로 연결된다. 각 상자에 붙은 설명이 역할을 요약한다. View는 "뷰 컨트롤러도 비즈니스 로직도 모르며, 더 많은 시나리오에 쓰일 수 있다". Viewcontroller는 "뷰를 정의하지 않고 뷰에 의존하며, 뷰를 비즈니스 로직과 연결하고, 라이프사이클 변화에 따라 업데이트를 일으킨다".

> **(p.65)** *"뷰 컨트롤러의 새 목적은 오직 비즈니스 로직을 뷰에 붙이고 라이프사이클 변화에 반응하는 것입니다. 뷰모델의 책임 일부를 되찾아 오는 셈입니다."*
>
> *"대부분의 비즈니스 로직은 UI 도메인 **밖에** 살고, 뷰는 이제 분리되어 있습니다. 결과적으로 뷰 컨트롤러는 가볍고 단순하게 유지되며, 더 이상 뷰모델이 필요하지 않습니다."*

그리고 이 구조를 세 분류로 다시 읽는다.

> **(p.66)** *"뷰 컨트롤러는 뷰를 담고 그것을 비즈니스 로직에 붙이므로, **기능 뷰**로 분류할 수 있습니다. 이렇게 분류하면 그 책임이 더 잘 드러납니다."*
>
> *"이 가벼운 해법을 우리 앱에 적용하면, 새로 도입한 `CourseViewController`는 별도의 `CourseView`(이 접근에서는 여전히 명령형)에 의존하게 됩니다. 그러면 `CourseView`를 **기능 뷰**에서 **뷰 컴포넌트**로 강등할 수 있습니다. 여전히 똑똑하지만, 더 이상 비즈니스 로직을 알 필요는 없습니다."* (Figure 3.17)
>
> *"뷰를 강등하는 것은 대개 **좋은 일**이라는 점을 기억하세요. 우리 경우 `CourseView`는 더 단순해지고, 필요하다면 더 재사용 가능해집니다."*

> **(p.66) Note** — *"이 책의 나머지 부분은 주로 SwiftUI 같은 선언형 UI에 집중합니다."*

Figure 3.17은 Figure 3.10과 거의 같은 그림이다. 달라진 점은 하나뿐이다. Feature Views 상자에는 이제 `CourseViewController`가 있고, `CourseView`는 그 아래 새로 생긴 "View Components ('Smart', Has bindings)" 상자로 내려갔다. 모델 레이어(`CourseService`, `Course Model`)로 향하는 굵은 화살표는 이제 `CourseViewController`에서만 출발한다.

> **읽을 때 주의할 지점** — §3.8.1과 §3.8.6을 나란히 놓으면 이 챕터의 분류 기준이 가장 선명하게 드러난다. 뷰모델을 도입한 §3.8.1에서 `CourseView`는 **여전히 기능 뷰**였다. 모델까지 가는 경로가 한 홉 길어졌을 뿐 끊기지는 않았기 때문이다. 반면 뷰를 빼낸 §3.8.6에서 `CourseView`는 **뷰 컴포넌트로 강등**되었다. 모델로 가는 경로가 아예 사라졌기 때문이다. 즉 **간접화는 분리가 아니다.** 레이어를 하나 끼워 넣으면 의존이 간접적으로 바뀔 뿐이고, 의존의 방향을 바꿔야 분류가 바뀐다. 또 하나 눈여겨볼 점은 `CourseViewController`가 "기능 뷰"로 분류된다는 사실이다. 이 책의 분류는 타입의 종류(뷰인가 컨트롤러인가)를 따르지 않고 **역할**(비즈니스 로직과 뷰를 잇는가)을 따른다. 앎은 사라지지 않고 **한 곳으로 모일 뿐**이며, 이 절의 해법은 그 한 곳을 가장 얇은 타입으로 만드는 방법이다.

## § 3.9 UI 원칙 12: 기능 뷰가 항상 전체 화면인 것은 아니다

세 분류가 완성되자, 저자는 미뤄 둔 질문으로 돌아온다.

> **(p.66)** *"이제 우리는 세 가지 뷰 분류를 확립했습니다. **뷰 프리미티브**, **뷰 컴포넌트**, **기능 뷰**입니다."*
>
> *"그런데 왜 **기능 뷰**를 '화면'이라고 부르지 않는지 궁금할 수 있습니다."*
>
> *"다음 철학적 질문을 던질 때가 되었다는 뜻입니다. **화면이란 정말 무엇인가?**"*

일상적인 정의부터 확인한다.

> **(p.67)** *"모바일 엔지니어와 디자이너 모두 화면을 기기 위에서 작동하는 UI로 정의합니다. 일상적으로 '화면'은 폰의 픽셀, 포인트, 즉 화면 영역(real estate) 전부를 사용합니다. 어쨌든 기기의 화면이니까요."*
>
> *"예를 들어 우리 경우 `Course` 기능은 기기의 물리적 화면 전체를 차지하므로, 보통 **화면** 또는 **기능**이라고 부를 것입니다."*
>
> *"안타깝게도 이 패러다임은 뷰가 화면 전체를 차지하지 않는 순간 깨집니다."*

첫 번째 반례는 큰 화면 기기다.

> **(p.67)** *"한 가지 예는 패블릿이나 태블릿 같은 큰 화면 기기용으로 개발할 때입니다. 우리는 여러 '폰 화면'을 합쳐 하나의 '태블릿 화면'을 만드는 경우가 많습니다."*
>
> *"고전적인 예는 마스터-디테일 레이아웃입니다. 한쪽에는 요소 목록이 있고, 다른 쪽에서는 각 요소를 자세히 볼 수 있습니다. 폰에서는 둘 다 개별 화면이지만, 태블릿에서는 둘이 합쳐져 하나의 전체 크기 화면이 됩니다."* (Figure 3.18)
>
> **(p.68)** *"예를 들어 왼쪽에 코스 목록이, 오른쪽에 `CourseView`가 있을 수 있습니다. 이제 `CourseView`는 기술적으로 더 이상 화면이 **아닙니다**. 기기의 화면 전체를 쓰지 않기 때문입니다."*

두 번째 반례는 같은 뷰가 맥락에 따라 크기가 달라지는 경우다.

> **(p.68)** *"또 다른 예로, 위치 마커를 보여주는 지도 뷰가 '화면'일 수 있습니다. 한 맥락에서는 화면 전체를 차지하더라도, 다른 시나리오에서는 같은 지도 뷰가 화면의 50%만 차지할 수 있습니다. 그 경우 지도 뷰는 시각적으로 똑같은데도 '화면'이기를 멈춥니다."*
>
> *"이것은 역설적으로 '화면'이 항상 전체 화면 인터페이스와 동의어는 아니라는 뜻입니다."*
>
> *"그러니 우리가 무언가를 '화면'이라고 부를 때, 그것은 사실 '기능'에 관한 이야기라는 뜻이 됩니다. 그러나 그것도 항상 그렇지는 않습니다. 이유를 살펴봅시다."*

### § 3.9.1 모든 화면이 반드시 기능인 것은 아니다

이번에는 반대 방향의 반례다. 화면 전체를 차지하는데도 기능 뷰가 아닌 뷰들이 있다.

> **(p.68)** *"보통 '화면'을 말할 때는 비즈니스 로직을 가진다는 뜻을 담지만, 예외가 있습니다."*
>
> *"때로는 제목과 버튼만 있는 전체 화면 알림 뷰가 '화면'일 수 있습니다. 화면 전체를 쓰지만 기능은 최소한입니다. 이 책에서는 이런 '화면'을 UI 라이브러리에 적합한 **뷰 프리미티브**로 분류합니다."*
>
> *"다른 경우에는 사진 앨범을 보여주는 전체 화면 뷰인 사진 피커가 '화면'일 수 있습니다. 화면 전체를 쓰지만, 자신이 쓰이는 기능에 대해서는 **아무것도** 모릅니다. 사실 우리는 사진 피커를 여러 기능에 쓸 수 있는 **뷰 컴포넌트**로 분류합니다."*

두 반례를 합치면 "화면"과 세 분류는 **완전히 독립적인 축**이 된다.

| | 전체 화면이다 | 전체 화면이 아니다 |
|---|---|---|
| **기능 뷰** | 폰의 `CourseView` | 태블릿 마스터-디테일 속 `CourseView` |
| **뷰 컴포넌트** | 사진 피커 | 날짜 피커, `SelectionView`, 화면 절반을 차지하는 지도 뷰 |
| **뷰 프리미티브** | 제목과 버튼뿐인 전체 화면 알림 | `ImageLabelView`, `TextButton` |

여섯 칸이 모두 채워진다는 것은, "화면이다"라는 사실에서 그 뷰의 분류에 대해 **아무것도 추론할 수 없다**는 뜻이다.

> **(p.68)** *"이 구별은 '화면'이라는 용어가 뷰의 기능성과 분리되어 있고, 화면이 항상 비즈니스 로직과 묶여 있지는 않다는 점을 강조합니다."*
>
> *"전체 화면 뷰에 '화면'이라는 라벨을 붙이는 대신, 뷰를 **기능**이나 **기능성**의 관점에서 생각합시다. 그러면 그 뷰들이 전체 화면일 **수도 있고** 아닐 수도 있지만, 그것은 그다지 중요하지 않습니다. 그래서 우리는 뷰가 비즈니스 로직을 가진다는 것을 보여주기 위해 **기능 뷰**라는 용어를 씁니다."*

다만 저자는 일상 대화에서까지 "화면"이라는 단어를 금지하지는 않는다.

> **(p.68)** *"더 기술적인 수준에서 코드베이스를 추론할 때는 '화면'이라는 용어를 '뷰'와 혼동하지 않으려고 노력합니다."*
>
> *"그러나 실용적인 논의에서 전체 화면 뷰나 기능을 가리킬 때는 '화면'이나 '인터페이스'라는 용어를 쓰는 편이 유익합니다. 디자이너나 팀원과 이야기할 때는 '컴포넌트', '화면', '기능' 같은 용어로 전체 화면 기능성을 가진 뷰를 묘사하세요."*

요컨대 "화면"은 **대화의 단어**이고 "기능 뷰"는 **설계의 단어**다. 디자이너와의 대화에서는 화면이라고 말하되, 코드를 어디에 둘지, 무엇에 의존하게 할지를 판단할 때는 "이 뷰가 비즈니스 로직을 아는가"만 묻는다.

## § 3.10 결론

> **(p.69)** *"이제 우리가 도입한 여러 뷰의 역할, 스택 안에서의 책임, 비즈니스 로직에 대해 각 뷰가 아는 것을 분명히 이해했으므로, `CourseView` 구현으로 넘어갈 수 있습니다."*
>
> *"이 정보를 염두에 두고, 명령형 접근의 요소와 선언형 접근을 결합해 `CourseView`와 그 하위 뷰들의 구현을 시작할 것입니다."*
>
> *"방법론을 섞는 것은 이 챕터의 멘탈 모델이 여러 프레임워크에 일관되게 적용될 수 있음을 보여줍니다. 구현은 달라도, 뷰를 구성하는 접근은 대체로 비슷하게 유지됩니다."*
>
> *"이 챕터는 또한 우리가 쌓아 온 UI 원칙들의 모음을 마무리합니다. 다음으로는 그 원칙들을 코드로 실천하는 단계로 넘어갑니다."*

마지막 문장이 중요하다. **UI 원칙은 12번에서 끝난다.** Chapter 1의 원칙 1~4가 "UI를 언제, 얼마나 얇게 만들 것인가"를, Chapter 2의 원칙 5~7이 "뷰를 어떻게 이름 짓고 쪼갤 것인가"를, 이 챕터의 원칙 8~12가 "뷰가 무엇을 알게 할 것인가"를 정했다. 이후 챕터들은 새 원칙을 세우지 않고, 이 열두 원칙을 구현과 확장에 적용한다.

## § 3.11 챕터 요약

> **(p.70)**
> **세 가지 뷰 범주**
> - **뷰 프리미티브**: 라벨이나 버튼처럼 로직이 없거나 최소한인 단순한 뷰. 기능을 모른다.
> - **뷰 컴포넌트**: 로직이나 데이터 바인딩을 가진 똑똑한 뷰. 그러나 여전히 기능과 무관하다.
> - **기능 뷰**: 특정 비즈니스 로직과 기능에 연결된 뷰.
>
> **UI 원칙**
> - **UI 원칙 8**: 뷰 컴포넌트는 로직과/또는 바인딩을 가진다. "똑똑한" 뷰다.
> - **UI 원칙 9**: 뷰 컴포넌트는 비즈니스 로직을 모른다. 인터페이스나 클로저를 써서, 의존을 만들지 않고 컴포넌트를 비즈니스 데이터에 연결한다.
> - **UI 원칙 10**: 기능은 로컬 컴포넌트를 가질 수 있다. 재사용 가능성이 낮으면 컴포넌트가 특정 기능 안에 살 수 있지만, 미래의 유연성을 위해 기능과 무관한 상태를 유지해야 한다.
> - **UI 원칙 11**: 기능 뷰는 비즈니스 로직에 연결된다. 이 뷰들은 UI를 데이터 모델에 바인딩하고 비즈니스에 특화된 상호작용을 처리한다.
> - **UI 원칙 12**: 기능 뷰가 항상 전체 화면인 것은 아니다. "화면"이라는 개념은 유동적이므로, 뷰는 시각적 화면 영역이 아니라 기능성으로 분류해야 한다.
>
> **바인딩과 아키텍처**
> - 뷰를 비즈니스 로직에 연결하는 방법은 많다. 뷰모델, 컨트롤러, 선언형 바인딩, 상태 핸들러, 클로저, 퍼블리셔, 코디네이터.
> - 뷰모델 같은 추상화는 그것이 만드는 문제보다 더 많은 문제를 해결할 때 도입한다.
> - 명령형 코드에서는 컨트롤러에서 뷰를 추출해 둘 다 가볍고 집중된 상태로 유지한다.
>
> **재사용성 판단**
> - 위험 기반 휴리스틱을 쓴다. 시간 투자가 적고 복잡도가 낮게 유지된다면 컴포넌트를 미리 재사용 가능하게 만드는 것을 고려한다.
> - 가설적 시나리오를 위해 컴포넌트를 재사용 가능하게 만들지 **않는** 쪽에 건다.
> - 대부분의 뷰 프리미티브는 최소한의 노력(이름 바꾸기)으로 곧바로 UI 라이브러리에 둘 수 있다.

요약의 네 묶음은 챕터의 네 단계(분류 → 원칙 → 바인딩 → 재사용성)와 정확히 대응한다. 다섯 원칙을 하나로 압축하면 다음 한 문장이 된다. **비즈니스 로직에 대한 앎은 기능 뷰 한 곳에 모으고, 나머지 모든 뷰는 똑똑하든 멍청하든, 어디에 살든 그 앎으로부터 떼어 놓는다.**

## 안드로이드로 옮기면

이 챕터에는 책 자체의 코드가 없으므로, 여기서는 도해가 말하는 의존 구조를 Jetpack Compose 코드로 옮겨 본다. 흥미롭게도 책이 §3.8.4에서 Android를 직접 언급하는 만큼, 이 챕터는 안드로이드 개발자가 가장 자기 이야기처럼 읽을 수 있는 챕터이기도 하다.

### 세 분류의 Compose 등가물

| 분류 | Compose에서의 모습 | 예 |
|---|---|---|
| 뷰 프리미티브 | 원시 값과 콜백만 받는 stateless 컴포저블 | `Text`, `Button`, 직접 만든 `ImageLabelRow` |
| 뷰 컴포넌트 | 상태 홀더나 내부 로직을 갖지만 도메인 타입을 모르는 컴포저블 | Material3 `DatePicker` + `rememberDatePickerState()`, `SearchBar`, 직접 만든 `SelectionList` |
| 기능 뷰 | ViewModel이나 도메인 상태에 연결되는 컴포저블 | `CourseRoute`, 즉 `viewModel()`을 부르는 진입점 |

Material3의 `DatePicker`는 원칙 8·9의 교과서적인 예다. `DatePickerState`가 선택 날짜, 표시 월, 선택 가능 범위 같은 로직을 모두 품고 있지만, 그 날짜가 무엇에 쓰이는지는 전혀 모른다.

### 원칙 9 — 인터페이스로 끊기

책의 `SelectionElement`를 Kotlin 인터페이스로 옮기면 다음과 같다.

```kotlin
// :core:ui — UI 라이브러리가 인터페이스를 소유한다.
interface SelectionElement {
    val id: String
    val title: String
    val isSelected: Boolean
}

@Composable
fun SelectionList(
    items: List<SelectionElement>,
    onToggle: (id: String) -> Unit,   // 위로 올라가는 방향은 콜백이 끊는다.
    modifier: Modifier = Modifier,
) {
    LazyColumn(modifier = modifier) {
        items(items, key = { it.id }) { item ->
            SelectionItemRow(
                title = item.title,
                checked = item.isSelected,
                onCheckedChange = { onToggle(item.id) },
            )
        }
    }
}
```

`items`로 내려오는 방향은 인터페이스가, `onToggle`로 올라가는 방향은 콜백이 끊는다. §3.2의 "읽을 때 주의할 지점"에서 본 두 방향이 그대로 두 매개변수로 나타난다.

### 원칙 10 — 로컬 컴포넌트와 `internal`

Kotlin에는 Swift에 없는 편리한 도구가 하나 있다. `internal` 가시성 한정자는 "이 뷰는 이 기능 모듈 안에서만 쓴다"는 원칙 10의 결정을 **컴파일러가 강제하는 규칙**으로 바꿔 준다.

```kotlin
// :feature:course 모듈 — 기능 폴더에 살지만, Course를 모른다.
@Composable
internal fun ScheduleCard(
    dateText: String,
    timeText: String,
    onJoinCall: () -> Unit,
    onReschedule: () -> Unit,
    modifier: Modifier = Modifier,
) { /* ... */ }
```

매개변수에 `Course`나 `Tutor`가 없다는 점이 핵심이다. 나중에 다른 기능에서 필요해지면 `internal`을 지우고 `:core:ui`로 파일을 옮기기만 하면 된다. 이것이 원칙 10이 말한 "이동 비용이 0에 가까운 설계"다.

### 가벼운 뷰 컨트롤러(§3.8.6)의 등가물 — Route와 Screen 분리

§3.8.6의 구조는 Compose 공식 샘플(Now in Android 등)이 쓰는 **Route/Screen 분리** 관례와 정확히 같은 모양이다. `CourseRoute`가 `CourseViewController`의 자리에 서고, `CourseScreen`이 강등된 `CourseView`의 자리에 선다.

```kotlin
// 기능 뷰: 비즈니스 로직(ViewModel)을 아는 유일한 자리.
// 라이프사이클을 인지하며 상태를 수집하고, 뷰와 로직을 잇기만 한다.
@Composable
fun CourseRoute(viewModel: CourseViewModel = viewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    CourseScreen(
        uiState = uiState,
        onToggleTodo = viewModel::toggleTodo,
        onJoinCall = viewModel::joinCall,
    )
}

// 강등된 뷰 컴포넌트: 똑똑하지만 ViewModel도 CourseService도 모른다.
// 프리뷰와 UI 테스트는 이 함수만 대상으로 삼으면 된다.
@Composable
fun CourseScreen(
    uiState: CourseUiState,
    onToggleTodo: (id: String) -> Unit,
    onJoinCall: () -> Unit,
) { /* ImageLabelRow, CalloutCard, ScheduleCard, SelectionList 조립 */ }
```

Figure 3.16의 세 상자에 대응시키면, `CourseRoute`가 Viewcontroller(라이프사이클 + 연결), `CourseScreen`이 View(아무것도 모름), `CourseViewModel` 너머의 저장소·유스케이스가 Business logic이다. 책의 "뷰를 강등하는 것은 대개 좋은 일"이라는 말은 Compose에서 **"stateless 컴포저블은 프리뷰와 테스트가 쉽다"**는 익숙한 이점으로 나타난다.

### 뷰모델 판정(§3.8.2~3.8.4)을 안드로이드에서 읽을 때

이 부분은 그대로 옮기면 오독하기 쉽다. 책이 `CourseViewModel`을 "얕은 추상화"라며 뺀 근거는 **관심사 분리로 얻는 이득이 없다**는 것이었다. 그런데 Jetpack `ViewModel`을 쓰는 이유는 대개 관심사 분리가 아니라, 책이 §3.8.4 세 번째 항목에서 스스로 인정한 **라이프사이클과 구성 변경 대응**이다. 회전해도 살아남는 상태, `viewModelScope`로 묶이는 코루틴, `SavedStateHandle`을 통한 프로세스 종료 복원 등이 여기에 해당한다.

따라서 안드로이드에서 §3.8.2의 교훈은 "ViewModel을 빼라"가 아니라 다음처럼 읽는 편이 정확하다.

- **ViewModel은 두되, 두껍게 만들 이유를 따로 찾아라.** 라이프사이클 때문에 존재하는 ViewModel이 도메인 로직까지 떠안으면, 책이 경계한 "Massive View Controller"의 안드로이드판이 된다.
- **ViewModel과 UI 사이에 또 한 겹을 끼우지 마라.** `CourseViewModel` → `CourseUiMapper` → `CourseScreenPresenter`처럼 레이어를 쌓는 것은 책이 말한 "만드는 문제가 더 많은 간접성"에 정확히 해당한다.
- **데이터 변환이 필요하면 §3.8.4 네 번째 항목을 따른다.** 서드파티 SDK 응답을 UI 상태로 바꾸는 일은 ViewModel이 맡을 수 있지만, 여러 화면에서 같은 변환이 필요해지면 도메인 레이어의 매퍼나 유스케이스로 내린다.

### 원칙 12 — 적응형 레이아웃과 `XxxScreen` 관례

책의 마스터-디테일 예시는 Material3 Adaptive의 `ListDetailPaneScaffold`로 그대로 재현된다. 폰에서는 목록과 상세가 각각 전체 화면이지만, 태블릿과 폴더블에서는 한 화면의 두 창(pane)이 된다. 이때 상세 창에 들어가는 컴포저블이 "화면"인지 아닌지는 기기에 따라 달라지므로, 책의 말대로 분류 기준이 될 수 없다.

사진 피커 예시도 안드로이드에 그대로 있다. 시스템 Photo Picker(`ActivityResultContracts.PickVisualMedia`)는 전체 화면을 차지하지만 호출한 기능을 전혀 모르는, 원칙 12가 말한 **전체 화면 뷰 컴포넌트**의 실례다.

한 가지 긴장은 짚어 둘 만하다. 안드로이드 생태계는 `CourseScreen`, `HomeScreen`처럼 **`Screen` 접미사를 붙이는 관례**가 매우 강하다. 책의 기준으로 보면 이 이름은 크기에 대한 주장을 담고 있으므로 원칙 12와 부딪힌다. 다만 책도 "실용적인 논의에서는 화면이라는 단어가 유익하다"고 인정했으므로, 관례를 버릴 필요까지는 없다. 대신 **`Screen`이라는 접미사가 분류를 알려 주지 않는다**는 점만 기억하면 된다. 위의 Route/Screen 예시처럼, 같은 "Screen"이라도 ViewModel을 아는 쪽(`Route`)과 모르는 쪽(`Screen`)은 서로 다른 분류에 속한다.

### 다만 조금 다른 것

**소급 준수(retroactive conformance)의 부재.** Figure 3.3에서 `TodoItem`은 UI 라이브러리의 `SelectionElement`를 따른다. Swift에서는 `extension TodoItem: SelectionElement {}`를 Course UI 쪽 파일에 선언해서, 모델 타입 정의는 건드리지 않고도 준수 관계를 붙일 수 있다. 그러나 Kotlin에는 기존 클래스에 인터페이스를 나중에 붙이는 문법이 없다. `data class TodoItem(...) : SelectionElement`라고 쓰는 순간 **도메인 모델 모듈이 `:core:ui`에 의존**하게 되고, 이는 Book 0부터 지켜 온 "도메인은 UI를 모른다"는 방향을 뒤집는다.

그래서 멀티모듈 안드로이드 프로젝트에서는 책의 해법을 조금 변형해야 한다.

```kotlin
// :feature:course — 기능 UI 모듈에서 도메인 → UI 인터페이스로 매핑한다.
private fun TodoItem.toSelectionElement() = object : SelectionElement {
    override val id = this@toSelectionElement.id
    override val title = this@toSelectionElement.title
    override val isSelected = this@toSelectionElement.isDone
}
```

또는 인터페이스 대신 UI 모듈 쪽 `data class SelectionItem(id, title, isSelected)`를 두고 기능 모듈에서 변환하는 방법도 흔하다. 어느 쪽이든 **변환 코드가 기능 UI 모듈에 산다**는 점이 핵심이며, 이것은 Chapter 2의 팩토리·익스텐션이 기능 도메인에 살던 것과 같은 배치다. 책이 원칙 9를 "인터페이스**나 클로저**"라고 느슨하게 요약한 것도, 언어마다 가장 자연스러운 끊는 도구가 다르다는 점을 감안한 표현으로 읽을 수 있다.

## Ch2와의 관계, 그리고 Ch4로

**Ch2가 "모르게" 만든 것을 Ch3가 "어디서 알게 할지"로 완성한다.** Ch2는 원칙 5~7로 뷰의 이름과 분해를 다뤘고, 그 결과 거의 모든 뷰가 아무것도 모르는 프리미티브로 남았다. 그러나 앱은 결국 비즈니스 로직과 만나야 한다. 이 챕터는 그 만남을 금지하지 않고, **한 곳으로 모은다.** 원칙 8은 "똑똑함"을 허락하고, 원칙 9는 그 똑똑함에서 비즈니스 지식을 떼어 내며, 원칙 11은 비즈니스 지식이 모이는 단 하나의 자리를 기능 뷰로 지정한다.

두 챕터를 잇는 가장 분명한 연결 고리는 `SelectionView`다. Ch2는 이 뷰를 이름 짓기와 분해의 관점에서 다뤘다(`TodoListView` → `SelectionView`, 제목과 리셋 버튼을 밖으로). Ch3는 같은 뷰를 앎의 관점에서 다시 본다(프리미티브가 아니라 컴포넌트, `TodoItem` 대신 `SelectionElement`). 그리고 §3.4.1은 Ch2가 뷰들을 곧바로 UI 라이브러리에 둔 결정을 "투자가 거의 0이었기 때문"이라고 **소급해서 정당화**한다. Ch2가 원칙으로 먼저 행동했고, Ch3가 그 행동의 비용 논리를 뒤늦게 제공한 셈이다.

Ch1과의 연결도 선명하다. Ch1 §1.4.3의 어댑터는 도메인을 지키려고 UI 옆에 번역기를 두었고, Ch2 §2.2의 팩토리·별칭·익스텐션은 UI 프리미티브를 지키려고 기능 도메인 안에 번역기를 두었다. 이 챕터의 `SelectionElement`와 §3.8.4의 변환 뷰모델도 같은 계열의 번역기다. 세 챕터가 반복해서 묻는 질문은 결국 하나다. **"이 타입이 저 타입의 사정을 알아야 하는가? 알 필요가 없다면 그 사이에 무엇을 끼워 끊을 것인가?"**

**Ch4로 넘어가며.** 이 챕터는 스스로 "다이어그램이 많고 코드는 없다"고 밝혔고, 원칙 목록을 12번에서 닫았다. §3.2는 바인딩의 구체적인 방법(클로저, `@Binding`)을 "다음 챕터에서 코드 수준으로" 다루겠다고 미뤘고, §3.7은 `CourseView`가 `CourseService`에서 `Course`를 **어떻게** 받아올지를 아직 정하지 않았다고 명시했다. §3.10은 명령형과 선언형 요소를 섞어 `CourseView`를 구현하겠다고 예고한다. 즉 Ch4("UI를 실용적으로 구현하기")는 새로운 원칙을 세우는 챕터가 아니라, 이 챕터가 그린 Figure 3.10의 모든 화살표를 **실제 코드의 의존으로 옮기는** 챕터다. 이 챕터가 그은 것이 *뷰·컴포넌트·기능 뷰 사이의 앎의 경계*라면, 다음 챕터가 할 일은 *그 경계를 넘나드는 데이터 흐름을 실제로 배선하는 것*이다.
