### UI Principle 8: View components contain logic and/or bindings

- 이전 챕터에서 view primitives 를 둠으로써, UI 라이브러이에 배치할 수 있었다.
- 이번 챕터에서는 데이터 바인딩을 이해하고 있거나, 자체적인 내부 로직을 캡슌화한 형태의 뷰를 뷰 컴포넌트라고 칭한다.

#### Distinguishing view primitives from view components

- 뷰 컴포넌트의 대표적인 예는 네비게이션 바, 컬러 피커, 날짜 스케줄러 등이 있다.
- 자신이 구체적으로 어떤 기능에서 쓰이는지는 모르지만, 이 컴포넌트들을 다른 기능들에서 재사용할 수 있다.
- 따라서, UI 라이브러리에 위치시킬 수 있다.
- 명확성을 위해 View Primitive, View Component 두 계층으로 나눈다.

### UI Principle 9: View components remain unaware of business logic

- 뷰 컴포넌트로 분류하면, 내부에서 일정 수준의 자체 로직을 처리해야 한다.
- 하지만 뷰 컴포넌트는 기능 모듈의 비즈니스 로직에 대해서는 몰라야만 한다.
- 공용 UI 라이브러리에 배치하기로 한 이상, 특정 비즈니스 로직을 알게 해선 안된다.
- 이를 이용한 간단한 해결책으로 인터페이스를 도입할 수 있다.

### Is making a reusable component worth it?

- 특정 뷰를 재사용 가능하게 만드려면 인터페이스를 분리하고 추상화 계층을 두는 노력을 해야 한다.
- 특정 기능에서만 사용한다면 인터페이스 없이 직접 사용하는 것도 방법이다.

### Deciding when to make reusable components

- 소프트웨어에는 YAGNI 원칙이 있지만 초기에 재사용 가능한 컴포넌트로 만들어서 리스크를 최소화하는 것도 좋은 방법이다.

#### A heuristic from making reusable components

- 재사용 가능하게 만들기 위해 막대한 공수를 쏟아부었음에도 다른 기능에서 사용하지 않을 수도 있고
- 재사용 가능하게 만드는 작업은 간단했지만, 컴포넌트 자체의 복잡성이 지나치게 증가할 수도 있다.
- 반면에 노력이 거의 들지 않고, 복잡성도 많이 증가하지 않는다면 시도해볼 만한 가치가 있다.

### UI Principle 10: Features can have local components

- 다른 기능 모듈에서 필요로 하지 않을 뷰는 기능 모듈에 둘 수 있다.
- 하지만 이후의 재사용 가능성을 위해, 여전히 해당 기능의 존재를 모르도록 설계해야 한다.

### UI Principle 11: Feature views are connected to business logic

- 피처 뷰는 비즈니스 로직을 통해 기능을 실질적으로 지원한다.
- e.g., Course를 직접 의존하는 CourseView

### Connecting views to data

- CourseView 처럼 유저가 직접 대면하는 기능은 자신이 사용하는 하위 뷰뿐만 아니라, 연관된 비즈니스 로직까지 모두 알고 있다.
- CourseView는 Course 모델을 명확히 인지하고 있기 때문에, 다른 뷰들보다 더 구체적이고 특화된 뷰이며 재사용성은 거의 없다.

### Bindings can come in many forms

- 뷰를 모델에 연결하는 방법은 수 없이 많다.
- e.g., 뷰모델, 컨트롤러, 선언형 바인딩, 상태 핸들러 등등

#### The classic viewmodel

- 뷰모델을 활용하면 로직을 뷰로부터 끌어내어 뷰모델로 만든다.
- 이렇게 하면 View가 모델에 직접적으로 의존하지 않고 간접적으로 의존하게 된다.

#### A separation of concerns

- 뷰모델을 배치하면 뷰는 모델 계층으로부터 한 단계 격리된다.
- 이러한 분리는 유연성을 제공하지만, 이미 대부분의 로직과 복잡성이 모델 레이어에 존재한다면 뷰모델은 그저 불필요한 간접 참조 계층의 추가가 된다.

#### Deciding if you need more layers of indirection

- 뷰모델과 같은 간접 참조 계층은 계층이 유발하는 복잡성보다, 해결해 주는 문제와 도전 과제가 더 클 때 도입을 검토해야 한다.

#### When viewmodels make sense

- 뷰모델처럼 중간 타입을 도입하는 것이 합당한 몇가지 이유가 있다
    - 재사용 가능한 뷰에 연결해서 뷰에서 비즈니스 로직을 완전히 분리할 때
    - 거대해진 뷰에서 로직을 덜어내서 작게 유지할 때
    - Android 처럼 플랫폼 특성상 기본적으로 요구될 때
    - 비즈니스 로직에서 넘어오는 데이터의 형태가 UI에서 소비하기 불편할 때

#### Imperative considerations

- 명령형 UI 환경에서는 뷰 관련 코드가 거대해질 수 있다.
- 예를 들어, iOS의 UIKit 환경에서의 뷰 컨트롤러는 생명주기를 직접 인식하기 때문에 비즈니스 로직을 뷰 컨트롤러에 넣기도 한다.
- 이 때 복잡도를 줄이기 위해 비즈니스 로직을 뷰 컨트롤러 밖으로 꺼내는 선택을 할 수도 있다.

#### Making imperative code leaner

- 피처 뷰와 뷰 컴포넌트를 구분했던 것과 똑같은 원칙을 적용하면 뷰 컨트롤러를 날씬하게 만들 수 있다.
- 뷰모델이라는 간접 참조 계층 없이도 코드베이스를 단순하게 유지할 수 있다.
- 뷰 컨트롤러의 크기를 줄이겠다고 새로운 타입과 디자인 패턴을 도입하는 대신, 단순히 뷰 자체를 분리하고, 뷰 컨트롤러가 이 분리된 뷰를 의존하게 만드는 것으로 충분하다.
- UI 레이어 내부에 비즈니스 로직이 거의 남지 않게 되면, 뷰 컨트롤러가 비즈니스 로직에 직접 의존하게 만들고, 뷰 컨트롤러가 모델의 데이터를 UI에 바인딩하는 구조를 취할 수 있다.
- 이제 뷰 컨트롤러의 새로운 목적은 생명주기 변화에 반응하여 뷰에 비즈니스 로직을 연결하는 것이다. 따라서 뷰 컨트롤러 자체를 피처 뷰로 분류할 수 있다.

### UI Principle 12: Feature views aren’t always full-screen

- 피처 뷰가 꼭 화면 전체를 의미하는 것은 아니다.
- 작은 화면에서는 CourseView가 전체 화면을 차지할 수도 있지만 태블릿처럼 큰 화면에서는 일부를 차지하게 된다.
- 관습적으로 우리가 화면이라고 부르는 것은 실질적으로는 전체 화면 여부가 아니라 기능에 가까운 것일 수 있다.

#### Not every screen is necessarily a feature

- 모든 화면이 비즈니스 로직을 품고 있는 것은 아니다.
- 때로는 디바이스 전체 화면을 가득 채우면서도 타이틀과 버튼 하나만 있는 전체 화면 경고 뷰일 수도 있다.
- 이러한 화면은 비즈니스 로직이 전혀 없으므로 UI 라이브러리에 둘 수 있는 View Primitive로 분류할 수 있다.
- 따라서 전체 화면을 차지한다고 해서 screen이라고 부르기보다는 기능의 관점에서 바라보는 것이 중요하다.

### What we covered

- 3가지 View 카테고리
    - View primitives: 라벨이나 버튼처럼 비즈니스 로직이 거의 없는, 피처의 존재를 모르는 뷰
    - View components: 자체적인 내부 로직이나 데이터 바인딩을 품고 있지만, 특정 비즈니스 피처 지식은 모르는 범용 컴포넌트
    - Feature views: 특정 비즈니스 로직 및 피처 도메인과 직접 연결되어 있는 뷰
- UI 원칙
    - UI 원칙 8: 뷰 컴포넌트는 로직 그리고/또는 바인딩을 포함한다.
    - UI 원칙 9: 뷰 컴포넌트는 비즈니스 로직을 전혀 몰라야 한다. 인터페이스나 람다를 통해 의존성 없이 비즈니스 데이터를 연결해야 한다.
    - UI 원칙 10: 피처는 로컬 컴포넌트를 가질 수 있다. 미래에 다른 피처에서 사용될 가능성을 위해 비즈니스 로직으로는 독립되어야 한다.
    - UI 원칙 11: 피처 뷰는 비즈니스 로직과 연결된다. 이러한 뷰는 UI를 데이터 모델과 연결하여 비즈니스 상호 작용을 처리한다.
    - UI 원칙 12: 피처 뷰가 항상 전체 화면인 것은 아니다. 스크린의 개념은 유동적이기에 화면 면적이 아닌 기능을 기준으로 분류해야 한다.
- 바인딩과 아키텍처
    - 뷰를 비즈니스 로직에 연결하는 방법은 다양하다: 뷰모델, 컨트롤러, 선언형 바인딩, 람다 등등
    - 뷰모델과 같은 간접 참조 계층은 해당 계층이 유발하는 복잡성보다 해결해주는 문제가 많을 때 도입해야 한다.
    - 명령형 UI 환경에서는, 뷰를 컨트롤러에서 추출함으로써 둘 다 날씬하고 각자의 책임에 집중되게 만들 수 있다.
- 재사용성 판단 기준
    - 리스크 기반 휴리스틱을 사용하라. 시간 투자가 적고 복잡도가 낮게 유지된다면, 컴포넌트를 초기부터 재사용 가능하게 만들어라
    - 막연한 가상의 시나리오를 대비하겠다고 컴포넌트를 복잡한 재사용 구조로 만들지 마라
    - 대부분의 View primitive는 그저 이름을 범용적으로 지음으로써 공용 UI 라이브러리로 이동시킬 수 있다.
