아래처럼 **볼드 처리한 핵심 내용만 남기고, 흐름이 이어지도록 최소한의 연결만 추가해서** 정리할 수 있습니다.

# 1 UI 프레임워크와 아키텍처, 그리고 여러 제품 지원하기

> **가장 좋은 UI 아키텍처는 비즈니스 로직을 잃지 않고 버릴 수 있는 아키텍처다.**

UI 프레임워크나 아키텍처 자체보다 중요한 것은 **비즈니스 로직을 UI와 얼마나 잘 분리해 두었는가**이다.

---

## 1.1 UI 구현을 미룬다

**앱이나 기능 개발 초기에는 UI보다 요구사항과 도메인을 깊이 이해하는 데 집중하는 편이 낫다.**

UI 구현을 뒤로 미루면 특정 UI 프레임워크나 아키텍처에 얽매이지 않고 기능 자체에 집중할 수 있다.

그 결과:

* **기능과 비기능 요구사항을 더 깊이 이해할 수 있다.**
* UI뿐 아니라 서버 오류 처리, 우선순위 등 **전체 시스템 관점에서 판단할 수 있다.**
* **비즈니스 로직이 UI 계층으로 들어가는 것을 자연스럽게 막을 수 있다.**
* **모듈화하기 쉬워진다.**
* **비즈니스 로직을 단위 테스트하기 쉬워진다.**
* **여러 플랫폼을 지원하기 쉬워진다.**

즉, UI 구현을 미루는 것만으로도 **비즈니스 로직과 UI의 분리를 자연스럽게 유도할 수 있다.**

---

## 1.2 UI 아키텍처는 나타났다가 사라진다

어떤 프레임워크와 패턴을 선택하더라도 **대부분의 유명 UI 아키텍처는 비슷한 문제를 서로 다른 방식으로 해결한다.**

따라서 지나치게 복잡한 아키텍처를 처음부터 도입할 필요는 없다.

**단순한 문제에는 단순한 해결책을 사용하고, 그것으로 부족할 때 복잡한 아키텍처를 고려한다.**

### UI 아키텍처의 역할

UI 아키텍처는 **비즈니스 도메인과 UI 도메인을 연결하는 접착제**다.

어떤 것이 절대적으로 더 좋은지를 따지기보다 **팀의 개발 방식을 맞추고 코드를 예측 가능하게 만드는 합의 도구**로 보는 것이 좋다.

서드파티 프레임워크를 사용할 수도 있지만, 학습·유지보수·마이그레이션 같은 숨은 비용이 있다. 따라서 **특정 프레임워크에 의존하지 않는 기본 코드의 장점도 고려해야 한다.**

### 완벽한 UI 아키텍처는 없다

UI 문제가 생기는 이유는 대개 “잘못된 아키텍처” 때문이 아니라 다음과 같은 경우다.

* 작은 앱에 지나치게 복잡한 아키텍처를 적용한 경우
* **비즈니스 도메인과 UI 도메인이 강하게 결합된 경우**
* 최신 아키텍처를 계속 따라가느라 팀의 학습 비용이 커진 경우
* 기존 코드베이스에 특정 아키텍처를 억지로 적용한 경우

**기능 변경이 어렵거나 비즈니스 로직 테스트에 UI 테스트까지 필요하다면, UI 아키텍처 자체보다 구조적인 결합 문제가 원인일 가능성이 높다.**

또한 아키텍처는 기능이나 도메인마다 다를 수 있으며, 하나의 앱 안에 여러 방식이 공존하는 것도 자연스럽다.

중요한 것은 **비즈니스 계층이 UI 계층보다 변화에 덜 영향을 받도록 만드는 것**이다.

---

# 1.3 기능을 명령줄 도구라고 상상한다

비즈니스 로직을 어디에 둬야 할지 애매할 때 다음 질문을 해본다.

> **“이 기능이 UI 없이 명령줄 도구에서도 동작해야 한다면 어떨까?”**

이 사고 실험의 목적은 실제 명령줄 프로그램을 만드는 것이 아니라, **UI 없이도 모든 기능과 상태가 동작할 수 있는지 확인하는 것**이다.

Todo 완료/미완료 전환처럼 UI 없이도 의미가 있는 기능을 ViewModel이나 View 안에 넣으면 해당 기능이 UI에 종속된다.

따라서 이런 로직과 상태는 비즈니스 도메인으로 이동해야 한다.

그러면 비즈니스 도메인이 **단일 진실 공급원(Single Source of Truth)**이 되고, 동일한 기능을 스마트폰, 태블릿, 워치 등 다양한 환경에서 사용할 수 있다.

실제 명령줄 도구까지 만든다면 시뮬레이터나 UI 테스트 없이 네트워크 호출을 실행해 **디버깅과 통합 테스트**에도 활용할 수 있다.

---

## 1.3.2 비즈니스 로직을 분리하면 유연해진다

**비즈니스 로직을 UI와 분리하면 애플리케이션 자체가 독립적으로 동작할 수 있다.**

따라서 UIKit, SwiftUI 같은 UI 방식뿐 아니라 워치, TV, 백그라운드 처리, 명령줄 도구 등으로도 기능을 확장하기 쉬워진다.

---

## 1.3.3 비즈니스 도메인은 두껍게, UI는 얇게

기능의 일부만 비즈니스 도메인에 두고 나머지를 UI에 남기는 것이 아니라,

**전체 기능이 UI 없이도 독립적으로 동작하도록 만든다.**

UI 계층은 자주 바뀌지만 **비즈니스 로직은 상대적으로 오래 유지된다.**

따라서 UI와 비즈니스 로직을 최대한 분리하면 UI 프레임워크나 플랫폼 변화에 대응하기 쉬워진다.

---

# 1.4 UI가 비즈니스 도메인의 아키텍처를 결정하게 하지 않는다

**UI 프레임워크의 요구사항이 비즈니스 로직의 구조까지 결정하도록 해서는 안 된다.**

예를 들어 SwiftUI를 사용한다는 이유만으로 비즈니스 모델 전체를 `@Observable`로 만들거나, React Native 때문에 비즈니스 코드에 Objective-C나 React Native 타입을 넣으면 비즈니스 계층이 특정 UI 기술에 종속된다.

비즈니스 계층은 두껍게 유지하고 UI 계층은 얇게 유지해야 한다.

---

## 1.4.1~1.4.2 UI 프레임워크가 비즈니스 로직을 오염시키는 경우

React Native 지원을 위해 `CourseService`에 React Native 전용 타입을 추가하면 **하나의 UI 프레임워크 때문에 순수한 비즈니스 코드가 변한다.**

SwiftUI 역시 `ObservableObject`, `@Published`, `@Observable` 등을 비즈니스 계층에 넣으면 **UI 요구사항이 모델 설계에 영향을 주게 된다.**

특히 `isLoading`, `courses` 같은 UI 상태까지 비즈니스 서비스가 관리하게 되면 책임도 증가한다.

---

## 1.4.3 작은 어댑터를 둔다

해결책은 **비즈니스 계층을 순수하게 유지하고 UI 가까이에 작은 어댑터를 두는 것**이다.

```text
UI Framework
     ↓
 Adapter
     ↓
Business Domain
```

`CourseService`는 UI 프레임워크를 모르도록 유지한다.

SwiftUI에서는 `CourseViewModel`, React Native에서는 전용 브리지 객체가 UI 요구사항을 담당한다.

단순한 단일 플랫폼 앱이라면 이런 분리가 반드시 필요하지 않을 수도 있다.

하지만 규모가 커지거나 여러 플랫폼·UI 패러다임을 지원한다면 **작은 어댑터를 두는 것이 적은 비용으로 비즈니스 도메인의 이식성·테스트 용이성을 유지하는 데 도움이 된다.**

핵심은 **UI를 비즈니스 도메인의 일부가 아니라 도메인을 사용하는 하나의 소비자로 보는 것**이다.

따라서 비즈니스 영역은 UI에 가장 적합한 구조가 아니라 **기능 자체에 가장 적합한 구조**를 가져야 한다.

---

# 1.5 여러 제품과 아키텍처 지원하기

**비즈니스 로직을 UI 밖에 두면 핵심 기능 위에 얇은 UI 계층이 놓이는 구조가 된다.**

```text
여러 UI / 플랫폼
      ↓
얇은 UI 계층
      ↓
공통 비즈니스 도메인
```

그러면 모바일, TV, 워치, 명령줄 도구 등 여러 제품이 동일한 핵심 로직을 사용할 수 있다.

UI 아키텍처는 핵심 로직을 둘러싼 **가벼운 계층**으로 생각하는 것이 좋다.

하나의 앱 안에 여러 UI 아키텍처가 존재해도 괜찮으며, **핵심 비즈니스 로직이 UI 밖에 있기 때문에 새로운 플랫폼이나 UI 기술로 확장하기 쉬워진다.**

---

## 핵심 원칙

1. **UI 구현을 미루고 먼저 요구사항과 비즈니스 도메인을 설계한다.**
2. **UI 아키텍처는 절대적인 정답이 아니라 팀의 합의를 위한 도구다.**
3. **“UI 없이도 이 기능이 동작해야 한다면?”이라고 생각해 비즈니스 로직의 위치를 판단한다.**
4. **UI 프레임워크가 비즈니스 도메인의 구조를 결정하게 하지 않는다.**
5. **비즈니스 도메인은 두껍게, UI 계층은 얇게 유지한다.**
6. **필요하면 UI와 비즈니스 도메인 사이에 작은 어댑터를 둔다.**
