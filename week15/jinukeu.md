# UI 01 UI 프레임워크와 아키텍처 정리 — 버릴 수 있는 UI를 만드는 법

> Mobile System Design 시리즈 Book 1 (Modular UI & UI Architectures) 의 첫 번째 챕터.
> 핵심 질문: *"어떤 UI 아키텍처를 쓸 것인가"라는 질문 자체를 덜 중요하게 만들려면 무엇을 해야 하는가?*

---

## 도입 — 디저트로 남겨둔 UI

Book 0 전체를 지나오는 동안 우리는 브리핑을 받고, 비즈니스 도메인에서 API와 컴포넌트를 설계하고, 테스트·데이터 모델링·도메인 모델링·추상화·다중 환경 지원·의존성 관리를 다뤘다. 그런데 저자가 먼저 이상함을 인정한다.

> **(p.3)** *"그러나 우리는 단 하나의 UI 컴포넌트도 전달하지 않았습니다. 모바일 개발자들은 보통 UI부터 시작하기 때문에, 이것이 이상하게 보일 수 있습니다."*
>
> *"그런데 우리는 여기서 UI를 디저트처럼 마지막까지 아껴두고 있습니다."*

이 챕터는 그 순서가 우연이 아니었음을 밝히는 자리다. 그리고 챕터의 결론을 도입부에서 한 문장으로 미리 던진다.

> **(p.3)** *"최고의 UI 아키텍처는 비즈니스 로직을 잃지 않고 **버릴 수 있는** 아키텍처다."*

이 문장이 챕터 전체의 좌표다. "가장 좋은 것"을 성능이나 학습 곡선이나 공식 지원 여부로 정의하지 않고, **폐기 가능성**으로 정의한다. 좋은 UI 아키텍처란 오래 지키는 것이 아니라 **버릴 때 아무것도 딸려 나오지 않는 것**이라는 뜻이다.

읽기 전에 용어 하나를 고정해 두는 편이 좋다.

> **(p.3) Note** — *"모바일 엔지니어들이 아키텍처를 이야기할 때, 그들은 종종 UI 아키텍처를 의미합니다. 이는 본서에서 `NetworkClient`나 `Calendar` 같은 비즈니스/기반 도메인에 적용되는 아키텍처와는 다릅니다."*

Book 0에서 "아키텍처"라고 하면 도메인 그래프와 의존성 구조를 뜻했다. 이 챕터부터 등장하는 "UI 아키텍처"는 MVC·MVVM·MVI처럼 **화면과 상태를 잇는 배선 방식**을 가리키는 별개의 말이다. 두 층위를 섞으면 챕터 내내 논지가 흐려진다.

그리고 이 책이 이 논쟁을 다루는 태도를 밝힌다.

> **(p.4)** *"모바일 개발 커뮤니티에서는 '최고의 패턴'이나 '왜 선언형 UI는 viewmodel을 (가져선 안 되는가)'에 대해 많이 이야기합니다. 하지만 이 책에서는 **이런 질문이 덜 중요해지도록** 앱을 추론할 것입니다."*
>
> *"이 챕터의 목표는 (…) UI 레이어가 **광고된 것보다 덜 중요할 수 있다**는 것을 보여주는 것입니다."*

논쟁에 참전해 승자를 가리는 것이 아니라, 논쟁의 판돈 자체를 낮추는 것이 목표다.

> 이 챕터에서 다루는 것: UI를 나중 단계에 구현할 때 얻는 이점 · UI 아키텍처가 왜 *계절성*이며 생각보다 덜 중요한가 · 비즈니스 로직을 UI로부터 분리하도록 강제하는 방법 · 앱을 명령줄 도구로 상상할 때 얻는 이점 · UI 아키텍처가 비즈니스 도메인의 아키텍처를 강요해선 안 되는 이유 · 프레임워크 요구사항(React Native, SwiftUI)이 비즈니스 로직을 어떻게 오염시킬 수 있는가 · 비즈니스 도메인을 순수하게 유지하기 위한 해결책으로서의 어댑터 패턴

## 네 원칙이 이루는 하나의 사슬

본론에 들어가기 전에 지도를 그려두면 각 절이 무엇을 맡았는지 보인다. 네 원칙은 병렬로 나열된 팁이 아니라 **하나의 논증이 네 단계로 전개된 것**이다.

| 원칙 | 맡은 역할 | 한 문장 |
|---|---|---|
| **원칙 1** (§1.1) | **실천** — 언제 할 것인가 | UI 구현을 미루면 비즈니스 로직이 자동으로 제자리에 놓인다 |
| **원칙 2** (§1.2) | **해제** — 선택의 무게를 덜어냄 | 어차피 갈아엎히므로 UI 아키텍처 선택에 걸린 판돈은 크지 않다 |
| **원칙 3** (§1.3) | **도구** — 어떻게 판별할 것인가 | "명령줄 도구라면?"이라는 질문이 로직의 자리를 알려준다 |
| **원칙 4** (§1.4) | **방어** — 역류를 막음 | UI 프레임워크의 요구사항이 비즈니스 도메인을 변형시키지 못하게 한다 |
| §1.5 | **수확** | 그 결과 얇은 UI 레이어만 갈아 끼우며 여러 제품을 지원한다 |

원칙 1이 시간축의 처방이라면, 원칙 3은 그 처방을 일상에서 지킬 수 있게 해주는 검사 도구이고, 원칙 4는 반대 방향(UI에서 도메인으로)의 오염을 막는 차단막이다. 원칙 2는 이 셋이 왜 가능한지를 설명하는 전제에 가깝다.

## § 1.1 UI 원칙 1: UI 구현은 미루어라 — 규율 없이 분리를 얻는 법

절은 고백으로 시작한다.

> **(p.4)** *"이전 챕터들은 여러분의 뇌를 리팩토링하려 했습니다. 모바일 산업이 무의식적인 개발자들에게 주입하는 **UI-우선 프로그래밍**을 제거하려 한 것입니다."*
>
> *"우리가 UI와 무관한 (마이크로) 결정을 셀 수 없이 내려서 기능을 만들었다는 것을 알아차리셨길 바랍니다."*

Book 0 전체가 이 원칙의 실습이었다는 사후 고백이다.

**적용 범위를 먼저 못 박는다.** 이 원칙은 모든 상황에 대한 계율이 아니다.

> **(p.4)** *"**작은 앱에서는 UI를 즉시 만드는 것이 절대적으로 괜찮으며 매우 즐거울 수 있습니다.** 그러나 더 큰 조직이나 앱 안에서는, 보통 그것이 최우선이 아닙니다. 사실, **요구사항이 아직 완전히 명확하지 않을 때**는 시간 낭비일 수 있습니다."*

겨냥하는 것은 앱의 크기 자체가 아니라 **요구사항의 불확실성**이다. 주말에 혼자 만드는 앱에서 화면부터 그리는 것은 이 원칙의 위반이 아니다.

**미루면 UI 선택이 디테일로 내려앉는다.**

> **(p.5)** *"UI를 미룸으로써 처음에 우리가 UI를 어떻게 만드는지는 거의 *디테일*이 됩니다. 지금까지는 명령형 프로그래밍(예: UIKit)을 쓰든 선언형 프로그래밍(예: Jetpack Compose나 SwiftUI)을 쓰든 **중요하지 않았습니다.** 결과적으로, 우리가 어떤 아키텍처를 썼는지도 **중요하지 않았습니다.**"*

이것이 도입부의 "질문을 덜 중요하게 만든다"가 실제로 작동하는 방식이다. 논쟁을 이겨서가 아니라, **논쟁이 걸린 지점에 아직 도달하지 않았기 때문에** 중요하지 않다.

**여섯 가지 이점.** 저자가 나열하는 목록인데, 성격이 서로 다르므로 묶어서 보면 외울 필요가 없다.

| 축 | 이점 |
|---|---|
| **이해** | 기능과 비기능 요구사항을 더 잘 이해하게 된다. 색상·그림자·애니메이션 곡선 같은 UI 디테일에 빠지지 않는다 |
| **협업** | 안전한 "UI 거품"에서 벗어나 디자이너뿐 아니라 **팀 전체와의 협업**에 집중하게 된다. 무엇을 먼저 만들지 정렬하거나, 서버 통신 시 오류를 어떻게 다룰지 같은 논의 |
| **구조** | 비즈니스 로직이 자동으로 UI 레이어에 **없게** 된다. 관심사 분리를 강제하는 셈이다 |
| **모듈화** | 저수준 모듈로 분리하기로 하면 이미 준비되어 있다. **"import UI" 문이 0개**이기 때문이다 |
| **테스트** | 지금까지 작성한 모든 코드가 단위 테스트 가능하다. 비즈니스 로직이 완전히 비-UI 환경에 존재하기 때문이다 |
| **이식** | 필요시 여러 플랫폼을 더 쉽게 지원한다. 기능이 특정 타깃에 의존하지 않기 때문이다 |

뒤의 네 개(구조·모듈화·테스트·이식)는 사실 **같은 사실의 네 가지 얼굴**이다. `import UI`가 하나도 없다는 단일한 사실이 관심사 분리이자, 모듈 추출 준비 완료이자, 단위 테스트 가능성이자, 멀티플랫폼 대응이다.

**"조숙한 최적화 아닌가"라는 반문을 미리 막는다.**

> **(p.5)** *"우리는 *조숙한 최적화* 또는 코드를 '만일을 위해 재사용 가능하게' 만드는 것이 아닙니다. 우리는 단지 **UI를 나중 단계에 구현함으로써 우선순위를 다르게 두고 있을 뿐입니다.** 부수 효과로, 비즈니스 로직이 UI 도메인에 *새지* 않도록 보장합니다."*

이 구분이 중요하다. 재사용을 위해 추상화를 미리 짓는 것은 투자이고 비용이 든다. 그러나 순서를 바꾸는 것은 **추가 비용이 들지 않는다.** 그래서 절의 마지막 문장이 이 원칙의 진짜 매력을 말한다.

> **(p.5)** *"UI를 미룸으로써, 비즈니스 로직을 느슨하게 결합된 상태로 유지하기 위한 **정신적 에너지와 규율을 사용할 필요가 없습니다.** 아직 UI가 없으므로, 모든 비즈니스 로직이 자동으로 올바른 자리에 있게 됩니다."*

규율로 지키는 분리는 마감이 닥치면 무너진다. 순서로 얻는 분리는 무너질 것이 없다.

## § 1.2 UI 원칙 2: UI 아키텍처는 왔다가 사라진다 — 선택의 판돈을 낮추기

이 절은 긴 나열로 시작해 한 문장으로 기각한 뒤, 하나의 기준을 남기는 3단 구성이다.

**1단계, 나열.** UIKit 대 SwiftUI, XML 대 Jetpack Compose, Kotlin Multiplatform, React Native, 하이브리드 웹, 그리고 "M, V, C가 다양한 순서로 조합된" 약자들. 명령형·반응형·선언형·혼합. 그다음엔 "어떤 패턴을 써야 하지?"라는 후속 질문. 이 나열은 비교하자는 초대가 아니라 **얼마나 소모적인지 체감시키기 위한 장치**다.

> **(p.6)** *"옵션은 매우 많고 **선호의 지뢰밭**입니다."*

**2단계, 기각.**

> **(p.6)** *"하지만 여러분의 팀이 무엇을 결정하든, 결국 **가장 인기 있는 UI 아키텍처와 프레임워크는 모두 사용해도 괜찮으며, 비슷한 문제를 다른 풍미로 해결합니다.**"*

방점은 *flavor*(풍미)에 있다. 맛이 다른 것이지 영양가가 다른 것이 아니다. 즉 **어느 것을 고르느냐는 승부처가 아니다.**

**3단계, 남는 기준.**

> **(p.6)** *"그러나 단순함을 유지하세요. 요소 목록을 렌더링하기 위해 6글자 약자가 *필요하지* 않습니다. 그것은 **모기를 죽이려고 대포를 쏘는 격**입니다."*
>
> *"**단순한 해결책이 충분하지 않을 때만** 화려한 아키텍처 채택을 고려하세요."*

> **읽을 때 주의할 지점** — 여기서 남는 축은 **아키텍처 사이의 우열도, 팀의 익숙함도 아니다.** 오직 **복잡도의 필요성**이다. "대포"가 틀린 이유는 나쁜 무기라서가 아니라 지금 문제에 비해 과하기 때문이다. 그리고 이 기준은 조건부라는 점이 중요하다. "항상 단순하게"가 아니라 **"단순함이 충분한가를 먼저 묻고, 부족하면 올린다"**이므로, 복잡도가 실제로 정당한 기능에서는 같은 기준이 무거운 아키텍처를 승인한다. 익숙함·선호라는 축은 이 책에 분명히 등장하지만 그 자리는 바로 다음 절인 §1.2.1이다.

## § 1.2.1 UI 아키텍처를 정렬 도구로 보기 — 우열 논쟁의 해체

**UI 아키텍처의 정의부터 낮춘다.**

> **(p.6)** *"UI 아키텍처의 목적은 비즈니스 도메인과 UI 도메인 사이의 **'풀(glue)'** 역할을 하는 것입니다. 그것들 사이에서 선택하는 것은 종종 **선호와 경험의 문제**이며, 결과적으로 어느 것이 우월한지에 대한 입씨름이 일어납니다."*

"풀"이라는 격하가 이 절의 출발점이다. 접착제는 구조물이 아니라 구조물을 붙이는 재료다.

**그래서 다른 관점을 제안한다.**

> **(p.6)** *"UI 아키텍처를 더 건강하게 생각하는 방법은 그것들을 **팀 안에서의 정렬 도구**로 보는 것입니다. 코드를 더 예측 가능하게 만들어서, 팀이 **가치를 전달하는 데 더 집중**할 수 있게 합니다."*

측정 기준이 "이 아키텍처가 더 우월한가"에서 "이 아키텍처가 우리 팀의 코드를 예측 가능하게 만드는가"로 옮겨간다. 후자는 팀마다 답이 다를 수 있고, 그래서 논쟁할 이유가 사라진다.

**서드파티의 숨은 비용.** 탐구 자체는 권장하면서도 대가를 명시한다.

> **(p.6)** *"트렌디한 서드파티 아키텍처는 새로운 기술을 배우고 시야를 넓히는 데 좋습니다. 분명히 탐구할 가치가 있습니다."*
>
> *"그러나 (…) 그것들은 **퍼스트파티 프레임워크보다 더 자주 변합니다.** 최악의 경우, **새로운 멤버가 회사에 적응하는 데 걸리는 시간을 늘립니다.**"*

비용이 성능이나 용량이 아니라 **변경 빈도와 온보딩 시간**으로 계산된다는 점이 특징적이다. 그리고 대안을 제시한다.

> **(p.6)** *"서드파티 프레임워크를 좋아한다면 사용하세요. 하지만 **바닐라 코드 작성의 이점도 반드시 고려하세요.** 그러면 퍼스트파티 변경에 대해서만 걱정하면 됩니다."*
>
> *"퍼스트파티 변경을 다룰 때조차 우리는 이미 많이 마이그레이션해야 합니다."*

퍼스트파티만 따라가도 이미 벅차다는 것이 근거다.

## § 1.2.2 "완벽한" UI 아키텍처는 없다 — 오진을 막는 절

핵심 주장은 하나다.

> **(p.7)** *"UI 레이어에서 문제가 발생할 때, **'잘못된' 아키텍처를 선택했기 때문인 경우는 드뭅니다.**"*

**실제로 문제가 생기는 네 가지 상황.** 넷 다 아키텍처의 *정체*가 아니라 **사용 방식**에 관한 것이다.

1. 개발자들이 **작고 단순한 앱에 복잡한 아키텍처**를 사용할 때
2. 개발자들이 **비즈니스 도메인과 UI 도메인을 섞어**, UI 레이어가 비즈니스 도메인에 너무 강하게 결합되어 적응·재사용·분리가 어려워질 때
3. 개발자들이 **최신 새 아키텍처로 점프**하여, 팀이 새 패러다임을 배우도록 강요하고 가치 전달에서 산만해질 때
4. 개발자들이 **선호하는 아키텍처를 다른 코드베이스에 이식**하려 해 더 꼬인 코드베이스를 만들 때

**교체 충동이 생기는 순간과 그에 대한 판정.**

> **(p.7)** *"팀이 새 아키텍처를 구현해야 한다고 느낄 수 있는 때는 보통 **업데이트나 새 기능 추가가 어려울 때**, 또는 **비즈니스 로직을 테스트하기 위해 UI 테스트를 작성하는 등 코드 테스트에 어려움**이 있을 때입니다. 하지만 그 경우, '잘못된' UI 아키텍처가 이런 문제의 근원이 *아닐* 가능성이 큽니다."*

두 번째 계기(비즈니스 로직을 검증하려고 UI 테스트를 쓰고 있음)는 Book 0의 §5~§6과 정확히 맞물린다. 그 증상의 원인은 아키텍처 선택이 아니라 **로직이 UI에 얹혀 있다는 것**이고, 그것은 이 챕터의 원칙 1과 원칙 3이 다루는 문제다.

**그리고 범위를 아키텍처 밖으로 넓힌다.**

> **(p.7)** *"어쩌면 여러분이 직면한 문제는 UI 아키텍처와 *전혀* 관련이 없을 수 있습니다. 어쩌면 여러분의 프로젝트가 **문서가 부족하거나, 적절한 예제가 없거나, 트레이닝이 없거나, 나쁜 온보딩 경험, 해결되지 않은 의견 충돌, 또는 빈약한 코드 리뷰 문화** 때문일 수 있습니다."*
>
> *"여러분이 고른 UI 아키텍처는 **가까운 미래에 충분할 가능성이 큽니다.**"*

---

## § 1.2.3 UI 아키텍처와 트렌드 — 불안에 대한 답

> **(p.7)** *"'잘못된' 아키텍처를 골랐을까 봐 걱정한다면 두려워하지 마세요. **트렌드 아키텍처는 언제나 있을 것입니다.** 사람들은 어떤 아키텍처에서든, 심지어 오래된 것에서도 놀라운 일을 해냅니다."*

**"최고"의 정체를 밝힌다.**

> **(p.7)** *"'최고'의 아키텍처는 종종 **무엇이 트렌드인가**로 귀결됩니다. *현재* 사용되고 있는 것이 사람들이 채용되는 이유이고, 그것이 우리가 새 코드베이스에서 사용할 것입니다."*

기술적 우위가 아니라 채용 시장과 신규 프로젝트 관행이 "최고"를 정한다는 진단이다. 여기서 오래된 코드베이스에 대한 예측이 따라온다.

> **(p.7)** *"오래된 코드베이스에서 일한다면, **오래된 아키텍처와 새 아키텍처가 섞여 있을 거라 예상하세요.** (…) 이제 다양한 UI 아키텍처를 이해해야 합니다."*

**그럼에도 안전한 이유.**

> **(p.7)** *"그러나 **비즈니스 로직을 가능한 한 UI 도메인에서 멀리 떨어뜨리는 한, '코어 앱'은 UI 아키텍처에 너무 결혼하지 않습니다.** 이것이 UI를 더 가볍고 리팩토링하기 쉽게 만듭니다. 새 패러다임이나 **모바일 VR** 같은 완전히 새로운 플랫폼을 지원하는 등의 변화를 다루기 더 쉬워집니다."*

앞 절들이 "걱정하지 마라"고 했다면, 이 문장은 **걱정하지 않아도 되는 조건**을 명시한다. 조건은 하나뿐이다. 로직을 UI에서 멀리 두는 것이다.

## § 1.2.4 아키텍처는 시간에 걸쳐 형성된다 — 혼재의 정상화

> **(p.8)** *"아키텍처는 **기능이나 도메인마다 다를 가능성이 큽니다.** 예를 들어, 본서에서 `TodoList` 도메인은 명령형이고, `Network` 도메인은 파서를 위해 함수형 프로그래밍을 사용할 수 있으며, UI 도메인은 선언형 접근을 사용할 수 있습니다."*
>
> *"그런 다음 기능을 더 큰 앱에 후크하면, 그 모든 것을 함께 연결하기 위해 **또 다른 아키텍처**를 사용할 수 있습니다."*
>
> *"시간에 걸쳐 진화하며 다양한 기능에 걸쳐 다양한 아키텍처로 구성된 앱을 보는 것은 **정상이고 매우 흔합니다.**"*

혼재를 기술 부채로 규정하지 않고 정상 상태로 규정하는 것이 이 절의 일이다. 그리고 다음 절로 넘어가는 다리를 놓는다.

> **(p.8)** *"그러나 그것들은 모두 한 가지 공통점이 있습니다. **비즈니스 레이어는 UI 레이어에 비해 변화에 덜 취약합니다.** 이제 그것을 탐구해 봅시다."*

§1.2 전체가 "UI 아키텍처는 왔다 사라진다"를 논증했다면, 마지막 문장은 그 대비항인 "그럼 무엇이 남는가"를 지목하며 §1.3으로 넘긴다.

## § 1.3 UI 원칙 3: 기능을 명령줄 도구라고 상상하라 — 판별 도구

**왜 도구가 필요한가.**

> **(p.8)** *"종이 위에서는 비즈니스 로직을 뷰에서 분리하는 것이 명백하게 들릴 수 있습니다."*
>
> *"그러나 일상적인 작업 중에는, 특정 코드를 어디에 둘지 다시 흐려지기 쉽습니다. **시간 제약 때문에 지름길을 택하거나**, UI의 어떤 부분이 단순한 뷰로 구성되어야 하는지가 명확하지 않을 수 있습니다. 반대로, **어떤 뷰가 비즈니스 로직을 알아야 하고 데이터 바인딩을 포함해야 하는지 결정하기 어려워질 수 있습니다.**"*
>
> *"이 모든 것이 비즈니스 로직이 UI와 섞이도록 만들 수 있습니다. 결국 **한 가지 특정 사용 사례에만 사용 가능한 UI 컴포넌트**로 끝날 수 있습니다."*

원칙 자체는 자명한데 일상에서 지키기 어렵다는 진단이다. 그래서 판별 질문 하나를 처방한다.

> **(p.8)** ***"이 기능이 명령줄 도구로도 작동해야 한다면 어떨까?"***

**오해를 두 번 차단한다.**

> **(p.8)** *"우리 앱을 명령줄 도구로 생각하는 것은 우리가 **서버나 UI 없이(헤드리스 클라이언트로) 프로그램을 실행할 계획이라는 것을 의미하지 *않습니다*.** 그러나 그것은 **로직을 어디에 둘지 추론하고, 원할 때 UI 결정을 미루도록** 도와줍니다."*
>
> *"또한 **앱을 전달하기 위해 명령줄 도구를 만들어야 한다는 뜻도 아닙니다.** (…) 즉, 모든 기능과 상태가 UI *없이도* 사용 가능하다는 뜻입니다."*

이것은 아키텍처 요구사항이 아니라 **사고 장치**다. 결과물이 아니라 질문이 산출물이다.

## § 1.3.1 명령줄 위의 기능 — 장치를 실제로 돌려보기

**시나리오.** todo 항목을 완료/미완료로 토글하는 기능을 만든다. 자연스러운 충동은 그 로직을 UI 가까이 두는 것이다.

> **(p.9)** *"이 토글 로직을 **viewmodel이나 선언적 뷰에 구현할 수 있습니다.** 왜냐하면 그것이 UI 상호작용이 일어나는 곳이고 **상태가 가시적으로 변하는 곳**이기 때문입니다."* (Figure 1.1)

이 충동에는 나름의 근거가 있다는 점을 저자가 인정하고 넘어간다는 데 주목할 만하다. 상호작용과 상태 변화가 눈에 보이는 곳이 UI이기 때문이다.

**장치를 돌린다.** 아직 구현하지 않은, 그저 설계만 해본 CLI를 상상한다.

```
% course --fetch-subscribed-courses 1AAA5872-86C6-4501-948F-CC7A05FA8025
ED8F92E2-983C-4BCD-864C-E77257238C62, @CalebGuitar

% course --fetch-todos-for-course ED8F92E2-983C-4BCD-864C-E77257238C62
5885206E-1836-45B3-9E5F-93A60176852B, Transcribe verse of Stairway to heaven
ACB77219-DA08-4A1B-ACE9-E0F9BAE9B515, Find all C notes on the fretboard
63E2D8FE-0B1D-42FF-980B-706611948F58, Practice intro of smoke on the water
B5EE3633-23B5-4E19-9271-78E21702C621, Practice the G major scale

% course --toggle-todo ACB77219-DA08-4A1B-ACE9-E0F9BAE9B515
completed "Find all C notes on the fretboard"
```

> **(p.10)** *"명령줄 도구만 있다고 가정함으로써, 특정 비즈니스 로직이 viewmodel이나 선언적 뷰에 살아야 하는지 **의심할 필요가 없게 됩니다.** 거기에 두면 명령줄 도구가 기능을 놓칠 것이기 때문입니다."*
>
> *"이 경우, 이 작은 연습은 **viewmodel의 토글 로직이 `Course` 도메인에 살아야 한다**는 것을 알려줍니다."*

판별 도구가 실제로 판정을 내리는 순간이다. 마지막 명령이 동작할 수 없다면 로직의 자리가 틀렸다는 뜻이다.

**옮긴 뒤에 생기는 것.**

> **(p.10)** *"비즈니스 도메인에 상태를 저장하는 이점은 그것이 **단일 진실 공급원**이 된다는 것입니다. 이제 *어떤* UI 프레임워크, 아키텍처, 타깃(전화기, 태블릿, 시계)이든 서비스할 수 있습니다. 즉, 모델 도메인을 **자기 지속적(self-sustained)**으로 만들어 다른 레포로 이동시키거나 오픈소스화도 가능하게 합니다."* (Figure 1.2)

**Note 하나가 붙는다.**

> **(p.11) Note** — *"가상의 명령줄 도구를 만드는 것은 좋은 연습이지만, **실제로 출시하는 것은 더 가치가 있을 수 있습니다.** 시뮬레이터나 UI 테스트에 의존하지 않고도 **디버깅과 통합 테스트를 위한 많은 네트워크 호출을 발사할 수 있게** 해줍니다."*

> **읽을 때 주의할 지점** — 이 Note의 수혜자는 **클라이언트 개발자 자신**이다. 걷어내는 것이 "시뮬레이터"와 "UI 테스트"인데, 둘 다 서버 팀이 쓰지 않는 도구다. 즉 API 계약 검증을 남에게 넘긴다는 이야기가 아니라, 지금까지 화면 여정을 거쳐야만 도달하던 호출을 명령 한 줄로 반복·조합·자동화할 수 있게 된다는 이야기다. 그리고 이 Note는 절 본론의 부록이 아니라 **본론을 해냈을 때 따라오는 보상**이다. 로직을 도메인으로 내렸기 때문에 CLI가 만들어질 수 있고, CLI가 있기 때문에 디버깅이 빨라진다.

## § 1.3.2 비즈니스 로직 분리로 얻는 유연성 — 얻는 것의 목록

저자가 예제의 한계를 먼저 인정한다.

> **(p.11)** *"`Course` 예제는 작습니다. 그러나 이 사고 실험은 **비즈니스 로직을 어디에 둘지 명확하지 않을 때** 도움이 됩니다."*

그리고 분리가 실제로 무엇을 열어주는지 나열한다.

> **(p.11)** *"iOS 앱을 만들고 있다면, 우리 애플리케이션이 UIKit이나 SwiftUI 위에서 실행되는지가 **덜 중요합니다.** 우리 애플리케이션은 **자기 충족적**이며, 우리가 원하면 UIKit, SwiftUI, AppKit, Apple TV, Apple Watch, Apple Vision Pro, 위젯, App Clip, 헤드리스 클라이언트, 명령줄 도구 등에 사용할 수 있게 **'그저 그렇게 됩니다'.**"*
>
> *"백그라운드 지원, 즉 앱이 백그라운드 상태에서도 상태를 동기화하는 것을 구현하고 싶다면, 다시 말하지만 **UI 의존성 없이 훨씬 쉬울 것**입니다."*
>
> *"그 광범위한 목록만으로도 **회사의 미래 방향에 대해 더 민첩해질 것**임을 보여주어야 합니다."* (Figure 1.3)

"그저 그렇게 된다"(*it just so happens*)는 표현이 핵심이다. 이 목록은 추가 작업의 결과가 아니라 **로직이 UI 밖에 있다는 사실의 자동 귀결**이다.

## § 1.3.3 비즈니스 도메인은 두껍게, UI 도메인은 가볍게 — 처방의 강도와 근거

이 절에는 성격이 다른 두 덩어리가 들어 있다. 섞어 읽으면 논지가 흐려진다.

### 앞부분: 처방의 강도

> **(p.12)** *"비즈니스 도메인에서 기능의 80%를 끝내고 UI 도메인에 20%(예: todo 항목 완료 능력)를 남기는 것과 반대로, ***전체* 기능이 UI 없이 독립적으로 작동하는지** 확인합니다."*

80%로는 부족하다는 것이다. 왜 부족한지가 그다음에 나온다.

> **(p.12)** *"이 '명령줄 도구 사고방식'이 *조숙한 최적화*라고 생각할 수 있습니다. 그러나 일상 작업에서, 우리는 **viewmodel에 비즈니스 로직을 넣는 등 비즈니스 로직 일부를 UI 도메인으로 잘못 새는 것을 피해 갑니다.** 시간이 지나면서 앱은 ***천 번의 베임에 의한 죽음(death by a thousand cuts)***을 겪을 것입니다."*

한 번의 큰 실수가 아니라 **작은 누출의 누적**이 위험이라는 진단이다. 그래서 기준을 80%가 아니라 100%로 두어야 한다. 80%를 기준으로 삼으면 매번 "이 정도는 20% 안에 들어가겠지"라는 판단이 반복되고, 그 판단이 누적된다.

### 뒷부분: 처방의 근거

> **(p.12)** *"그래도 앱을 UI 없는 자체 시스템으로 생각할 가치가 있습니다. **영원히 폰만 지원하는 모바일 개발자라 해도, 여전히 상당한 변화와 마이그레이션을 경험할 수 있기 때문입니다.**"*

그리고 실제 목록을 든다.

> **(p.12)** *"그리 오래 전이 아닌데 iOS 커뮤니티는 **단일 화면 앱에서 화면당 다중 view controller로** 갔습니다. **단일 앱에서 확장, 위젯, App Clip이 있는 앱 생태계로** 갔습니다. *오직* 폰만 지원할 때조차, 모바일 엔지니어들은 **명령형에서 선언형 UI로** 갔습니다. UIKit에서 SwiftUI로의 마이그레이션, Android 엔지니어의 경우 **XML 레이아웃에서 Jetpack Compose로의 마이그레이션** 등. 그리고 그 뒤에도 Apple은 UI를 다시 **Liquid Glass**로 바꾸기로 결정했습니다."*
>
> *"**UI 레이어는 항상 무거운 변화를 겪고 있습니다. 그러나 비즈니스 로직은 거의 같은 상태로 남았습니다.**"*

> **읽을 때 주의할 지점** — 근거의 축은 **기기가 아니라 시간**이다. "폰만 지원해도"라는 조건절을 들으면 "그래도 기기는 여러 종류잖아"(화면 크기·해상도 파편화)로 반박하기 쉬운데, 저자가 말한 것은 파편화가 아니라 **변화와 마이그레이션**이다. 파편화는 한 시점에 여러 대상이 공존하는 문제이고, 마이그레이션은 한 대상이 시간에 따라 갈아엎히는 문제다. 목록이 전부 연대기순이라는 점이 이를 뒷받침한다.

```
[기기 축 — 저자가 말한 것이 아님]
        어느 한 시점
   작은 폰 · 큰 폰 · 폴더블
   → "동시에 여러 대상을 지원해야 한다"

[시간 축 — 저자가 말한 것]
   과거 ────────────────────────────▶ 현재
   단일화면 → 다중 VC → XML→Compose → Liquid Glass
   UI 레이어 :  갈아엎힘 → 갈아엎힘 → 갈아엎힘
   비즈니스   :  ────── 거의 그대로 ──────
```

**방치했을 때의 결말도 명시된다.**

> **(p.12)** *"비즈니스 로직 일부를 UI 레이어에 남겨 두었다면, 앞서 언급한 어떤 시나리오라도 지원하기 더 고통스러웠을 것입니다. **코드를 중복시키거나, 다양한 데이터를 동기 상태로 유지하기 위해 일을 복잡하게 만들거나, 어쨌든 코드를 비즈니스 도메인으로 옮겨야 했을 것입니다.**"*

세 번째 선택지가 뼈아프다. **결국 옮기게 되는데, 다만 마감에 쫓기면서 옮기게 된다.**

## § 1.4 UI 원칙 4: UI는 비즈니스 도메인의 아키텍처를 강요하지 않는다 — 역류 차단

원칙 1~3이 "로직을 UI에 두지 마라"였다면, 원칙 4는 **반대 방향의 오염**을 다룬다. 로직은 도메인에 잘 두었는데, 그 도메인의 *모양*이 UI 프레임워크의 요구에 맞춰 변형되는 경우다.

> **(p.12)** *"UI 아키텍처, 또는 UI 프레임워크조차 기저 아키텍처를 정의하도록 두는 것은 **매혹적입니다.**"*
>
> *"예를 들어, SwiftUI를 사용한다면 반응형 UI를 지원하기 위해 **모든 비즈니스 도메인 모델을 `@Observable`로** 만들 수 있습니다. 또는 React Native를 지원하고 싶다면, 이제 **Swift 비즈니스 모델에 `objc`와 `NSObject` 코드**를 추가해야 합니다."*

> **(p.13)** *"이것은 미묘한 문제를 만듭니다: **UI 프레임워크 요구사항이 비즈니스 로직을 정의할 위험**이 있습니다."*
>
> *"예를 들어, 우리가 UI에 사용하는 아키텍처라는 이유로 **전체 코드베이스를 반응형으로 만드는 것**입니다."*
>
> *"그러나 이전에 보았듯이, **비즈니스 레이어를 두꺼운 레이어로, UI를 얇은 레이어로 생각함으로써 더 많은 제품이나 타깃을 지원할 수 있습니다.** 이것은 우리를 더 민첩하게 유지합니다."*

"매혹적"이라는 단어가 정확하다. 이것은 게으름의 결과가 아니라 **선의와 일관성 추구의 결과**로 벌어진다. 절은 두 시나리오를 검토한 뒤 해법을 제시하겠다고 예고한다.

## § 1.4.1 React Native로의 브릿지 — 첫 번째 오염 사례

> **(p.13)** *"다른 플랫폼을 브리징할 때, Swift 코드는 종종 **Objective-C 호환**이어야 합니다. 우리는 `objc`와 `NSObject` 어노테이션을 사용해 이를 달성합니다."*
>
> *"추가로, React Native의 **`RCTPromiseResolveBlock` 같은 UI 프레임워크 특정 타입**을 지원해야 할 수 있습니다."*

```swift
// Business logic shaped by React Native bridge requirements
@objc final class CourseService: NSObject {
    @objc
    func fetchCourses(_ resolve: @escaping RCTPromiseResolveBlock,
                      reject: @escaping RCTPromiseRejectBlock) {
        // ... business logic forced into promise pattern
    }
}
```

오염이 두 겹으로 들어온다는 점에 주목할 만하다. 하나는 **언어 상호운용 요구**(objc·NSObject)이고, 다른 하나는 **특정 UI 프레임워크의 고유 타입**(RCTPromiseResolveBlock)이다. 뒤쪽이 더 나쁘다. 비즈니스 로직의 시그니처가 React Native를 알게 되기 때문이다.

> **(p.13)** *"이제 `CourseService`는 **'순수'하지 않게 됩니다.** 단 하나의 UI 프레임워크 지원을 위해 추가 요구사항을 포함합니다."*
>
> *"이는 좋은 의도로 진행하는 방법입니다. 그러나 다시 한번, **`CourseService`가 명령줄 도구의 일부였다면 이 코드는 말이 안 될 것입니다!**"*

원칙 3의 판별 도구가 여기서 다시 쓰인다. 네 원칙이 독립적이지 않다는 증거다.

## § 1.4.2 SwiftUI 지원 — 두 번째 오염 사례, 그리고 더 미묘한 형태

이 절은 **개선의 계단**을 보여준다는 점에서 앞 절과 성격이 다르다.

### 1단계: ObservableObject + @Published

```swift
import Combine

final class CourseService: ObservableObject {
    @Published var courses: [Course] = []
    @Published var isLoading: Bool = false
    @Published var errorMessage: String?

    func fetchCourses() -> AnyPublisher<[Course], Error> {
        // Business logic now forced into publisher pattern
    }
}
```

> **(p.14)** *"이는 여러 문제를 만듭니다. 첫째, **비즈니스 로직이 이제 Combine을 통해 UI 프레임워크 의존성을 요구합니다.** 둘째, **UI에 필요하지 않을 때조차 여러 속성이 observable이 됩니다.** 이 특정 예에서, `fetchCourses`는 이제 `[Course]` 대신 **publisher를 반환합니다.** 마지막으로, **우리 테스트가 반응형 스트림과 타이밍을 다뤄야 해서 오버헤드가 생깁니다.**"*

네 가지 문제가 모두 "UI가 원해서 도메인이 바뀐" 결과다.

### 2단계: @Observable

> **(p.14)** *"Apple은 이런 문제를 인식하고 마찰을 줄이기 위해 `@Observable`을 도입했습니다. (…) 이렇게 하면 `@Published` 속성을 제거할 수 있고 **더 이상 publisher를 반환할 필요가 없습니다.**"*

```swift
// Better, but still UI-influenced
@Observable
final class CourseService {
    var courses: [Course] = []
    var isLoading: Bool = false
    let networkClient: NetworkClient

    func fetchCourses() async throws -> [Course] {
        return try await networkClient.request("/courses")
    }
}
```

1단계의 네 문제 중 셋(Combine 의존, publisher 반환, 스트림 타이밍 테스트)이 실제로 해소된다. 그런데 저자는 여기서 멈추지 않는다.

### 3단계: 그럼에도 남는 것

> **(p.15)** *"`@Observable`은 *훨씬* 더 깨끗하지만, 여전히 **비즈니스 요구사항이 아닌 UI 필요에 의해 추동된 설계 결정**을 나타냅니다. **백그라운드 sync에서 호출되었을 때 `fetchCourses()`가 왜 observable이어야 합니까?**"*
>
> *"그러나 미묘하게 추가된 비용에 주목하세요: **`fetchCourses`가 이제 `isLoading`과 `courses` 상태를 유지하는 책임을 집니다.** 그것들이 동기화 상태를 유지하도록 보장해야 합니다."*

```swift
func fetchCourses() async throws -> [Course] {
    // fetchCourses is now in charge of keeping isLoading and
    // courses in a proper state.
    isLoading = true
    defer { isLoading = false }

    do {
        let fetchedCourses = try await networkClient.request("/courses")
        courses = fetchedCourses
        return fetchedCourses
    } catch {
        courses = []
        throw error
    }
}
```

`isLoading`은 **화면에 스피너를 띄우기 위한 값**이다. 그런데 그 값을 유지하는 책임이 비즈니스 메서드 안에 들어와 있다. 순수한 데이터 조회 함수였다면 없었을 상태 관리 코드가 절반을 차지한다.

절은 판별 질문으로 끝난다.

> **(p.15)** *"비-UI 컨텍스트에서 사용되는 *순수한* `Course` 라이브러리에서, 여전히 `@Observable`을 선택하시겠습니까? 이제 `CourseService`가 상태를 보유하고 그 속성을 노출하시겠습니까? **그 답이 UI 프레임워크가 우리의 아키텍처적 결정을 어떻게 형성하는지 드러냅니다.**"*

> **읽을 때 주의할 지점** — `@Observable`이 무엇을 고쳤고 무엇을 못 고쳤는지 구분하는 것이 이 절의 핵심이다. **고친 것**: Combine 의존성, publisher 반환, 반응형 스트림 타이밍 테스트. **못 고친 것**: 설계 동기가 여전히 UI에서 왔다는 사실, 그리고 비즈니스 메서드가 UI 상태(`isLoading`)의 동기화 책임을 떠안았다는 사실. 도구가 좋아져도 **누가 설계를 주도하는가**는 그대로라는 것이 논점이다.

## § 1.4.3 대안적 접근 — 어댑터 패턴

해법의 구조는 단순하다. **도메인은 순수하게 두고, UI 옆에 작은 번역기를 둔다.**

```swift
// 1) 순수한 비즈니스 도메인
final class CourseService {
    private let networkClient: NetworkClient
    func fetchCourses() async throws -> [Course] {
        // Pure business logic
    }
}

// 2-a) SwiftUI 어댑터
@Observable
final class CourseViewModel {
    private let courseService: CourseService
    var courses: [Course] = []
    var isLoading: Bool = false

    func loadCourses() async {
        isLoading = true
        defer { isLoading = false }
        do { courses = try await courseService.fetchCourses() }
        catch { courses = [] }
    }
}

// 2-b) React Native 브릿지 어댑터
@objc final class CourseServiceRN: NSObject {
    private let courseService: CourseService

    @objc
    func fetchCourses(resolve: @escaping RCTPromiseResolveBlock,
                      reject: @escaping RCTPromiseRejectBlock) {
        Task {
            let courses = try await courseService.fetchCourses()
            resolve(courses.map(\.dictionary))
        }
    }
}
```

§1.4.2에서 문제였던 `isLoading` 관리 코드가 사라지지 않았다는 점을 눈여겨볼 만하다. **자리를 옮겼을 뿐이다.** 도메인 메서드에서 어댑터로 옮겨갔고, 그래서 `CourseService.fetchCourses()`는 다시 순수한 조회 함수가 되었다.

**오버엔지니어링이라는 반문에 답한다.**

> **(p.17)** *"여러분은 궁금할 수 있습니다: **'이거 오버엔지니어링 아닌가? 단일 UI 프레임워크만 쓰는데 왜 어댑터를 만들지?'**"*
>
> *"답은 **앱의 범위에 달려 있습니다.** 다중 UI 패러다임이 결코 필요하지 않을 단순한 단일 플랫폼 앱이라면, **비즈니스 레이어에 프레임워크 요구사항을 추가하는 것은 받아들일 수 있습니다.** 특히 그것이 단지 `@Observable` 키워드일 뿐이라면."*
>
> *"그러나 더 복잡한 시스템을 만들거나 성장을 예상한다면, 어댑터 패턴은 **최소의 선행 비용으로 상당한 장기 이점**을 제공합니다."*

계율이 아니라 조건부 권고다. §1.2의 "단순함이 부족할 때만 올린다"와 정확히 같은 형태의 판단이다.

**그리고 관점 하나를 남긴다.**

> **(p.17)** *"UI를 **별개의 엔티티**로 생각하세요. 작은 어댑터를 사용해 **우리 도메인을 사용하는 또 다른 고객이나 *소비자***로 생각하세요."*
>
> *"그러나 그 아래에는 **그 기능에 *최선*인 아키텍처만** 가질 것이고, 단지 반응형 UI에만 맞는 것이 아닙니다."*

UI를 앱의 정점이 아니라 **도메인의 소비자 중 하나**로 재배치하는 것이 원칙 4의 결론이다.

## § 1.5 다양한 제품과 아키텍처 지원 — 수확

> **(p.17)** *"비즈니스 로직을 UI 레이어 밖에 두는 것을 보장하면, 위에 코어 기능과 얇은 UI 레이어로 끝나게 됩니다. UI 레이어는 (…) 다른 UI 패러다임을 지원하기 위한 ***심(shim)*** 또는 ***베니어(veneer)***와 같습니다."*

심과 베니어는 둘 다 **얇게 덧대는 것**을 뜻한다. 구조를 지탱하지 않으므로 뜯어내도 구조가 무너지지 않는다. 도입부의 "버릴 수 있는 아키텍처"가 여기서 구체적인 형태를 얻는다.

> **(p.17)** *"예를 들어, 앱을 Watch 앱이나 TV 앱으로 확장할 때 *선언형 UI*를 사용할 수 있습니다. 한편, 폰과 태블릿 같은 모바일 디바이스는 **명령형/반응형 접근**으로 `Course`를 구현할 수 있습니다. 우리는 *여전히* 앱과 서버 사이의 네트워크 연결을 테스트하는 데 사용할 수 있는 **명령줄 도구를 지원**합니다."* (Figure 1.4)

같은 코어 위에서 **타깃마다 다른 UI 아키텍처**를 쓴다. §1.2.4의 "혼재는 정상"이 여기서 설계 자산으로 전환된다.

**단기와 장기의 대비로 마무리한다.**

> **(p.18)** *"단기적으로는 어떤 아키텍처를 사용할지가 **정말 중요해 보일 수 있습니다. 어쨌든 결과를 전달해야 하니까요.**"*
>
> *"그러나 그래프를 보면, UI 아키텍처를 **코어 로직 주위의 가벼운 레이어**로 보는 것이 더 건강할 수 있습니다."*
>
> *"장기적으로, 오늘 일하는 UI 아키텍처가 애플리케이션에서 **큰 역할을 할 필요가 없을 것**입니다. 여러분의 앱은 다양한 UI 아키텍처를 포함할 수 있습니다."*
>
> *"시간이 지나면, 미래에 **VR 프레임워크** 같은 *더 많은* 아키텍처나 플랫폼을 지원할 수 있을 것이라 상상하기 어렵지 않습니다."*
>
> *"이것은 다시, **적절한 로직을 UI 레이어 밖에 유지함으로써** 가능합니다."*

마지막 문장이 챕터 전체를 하나의 조건으로 압축한다. 지금까지 나열한 모든 이점의 전제는 단 하나, 로직이 UI 밖에 있다는 것이다.

## § 1.6 챕터 요약

> **(p.19)**
> - **UI 원칙 1**: UI 구현은 미루어라. 시작 시점부터 비즈니스 로직을 UI에서 분리된 상태로 유지하는 데 집중하고, 우리가 무엇을 만들고 있는지에 대한 더 나은 아이디어를 얻을 수 있다.
> - **UI 원칙 2**: UI 아키텍처는 왔다가 사라진다. UI 아키텍처는 유행에 취약하다. UI 도메인을 가볍게 유지하는 데 집중하면 다음 아키텍처에 더 잘 대비된다.
> - **UI 원칙 3**: 기능을 명령줄 도구라고 상상하라. 비즈니스 로직을 UI 도메인 *밖에* 유지하는 것에 대해 더 잘 추론할 수 있다.
> - **UI 원칙 4**: UI는 비즈니스 도메인의 아키텍처를 *강요하지* 않는다. **어느 시점에서 앱이 둘 이상의 UI 아키텍처를 지원할 수 있기 때문이다.**
> - 대부분의 UI 아키텍처는 그것들이 해결하는 문제에 능숙하다. 대신, 그것들을 코드를 예측 가능하고 유지보수하기 쉽게 만드는 *팀 안의 정렬 도구*로 보라.
> - 비즈니스 로직이 UI 도메인으로 새지 않도록 강제하면 새 제품, 아키텍처, 또는 UI 패러다임을 지원하기 더 쉬워진다.
> - **여러분의 앱을 위에 얇은 UI 레이어가 있는 두꺼운 비즈니스 모델로 생각하라.** 그래야 새 UI 아키텍처, 프레임워크, 또는 패러다임으로 전환할 때 더 민첩하게 머무를 수 있다.

원칙 4에 붙은 이유("둘 이상의 UI 아키텍처를 지원할 수 있기 때문")가 §1.2.4와 §1.5를 그대로 호출한다는 점이 눈에 띈다. 요약이 각 원칙을 고립시키지 않고 서로 묶어둔다.

## 이번 학습에서 걸린 지점

시드 19개를 전부 출제한 결과, 첫 회차에서 1개, 재확인 회차에서 2개가 틀렸다. **세 오답이 같은 형태를 공유한다.**

### 세 오답의 공통 구조: 결론은 맞고 근거의 축이 어긋남

| 개념 | 이미 맞히던 결론 | 놓친 축 |
|---|---|---|
| §1.2 | 인기 아키텍처는 다 써도 괜찮다 | 판단 기준은 익숙함이 아니라 **복잡도의 필요성** |
| §1.3.1 | 토글 로직은 `Course` 도메인에 | CLI 출시의 수혜자는 서버 팀이 아니라 **클라이언트 개발자** |
| §1.3.3 | 두꺼운 비즈니스 · 얇은 UI | 근거는 기기 파편화가 아니라 **시간축의 UI 격변** |

세 번 모두 "무엇이 옳은가"는 맞았고 "**왜 그것이 옳은가**"에서 갈렸다. 그리고 세 오답 모두 **그럴듯한 이웃 개념으로 미끄러진 것**이라는 공통점이 있다.

- §1.2의 "익숙함"은 바로 다음 절 §1.2.1의 정렬 도구 논의에 실제로 등장하는 축이다. 인접한 절의 축을 가져온 것이다.
- §1.3.1의 "서버 팀 API 검증"은 CLI라는 도구에서 자연스럽게 연상되는 용도이지만, 본문이 걷어낸다고 한 것은 시뮬레이터와 UI 테스트다.
- §1.3.3의 "화면 파편화"는 "폰만 지원해도"라는 조건절에 대한 가장 자연스러운 반박 형태이지만, 저자는 기기가 아니라 시간을 말했다.

즉 **완전히 모르는 것이 아니라, 근처의 맞는 이야기를 끌어온 것**이다. 이런 오답은 개념을 다시 배우는 것보다 **각 주장의 근거가 어느 축 위에 있는지 한 번 짚는 것**으로 해소된다. 실제로 `lesson` 재교육 뒤 drill에서 세 개 모두 한 번에 통과했다.

### 굳히기 회차에서 확인된 것

마지막 굳히기는 역방향 적용 문항으로 구성했다. 같은 기준을 적용했을 때 **반대 결론**이 나오는 상황들이다.

- §1.2: 설정 화면에서는 무거운 아키텍처가 과했지만, 협업 편집(낙관적 업데이트·오프라인 큐·충돌 병합·되돌리기)에서는 **정당하다**고 판정
- §1.3.1: "도메인 모듈에 `main()`이 없다"는 증상 오진을 피하고 원인(로직이 UI에 갇혀 있음)을 지목
- §1.3.3: A팀/B팀 반사실 비교에서 저자의 결말 예측(코드 중복 · 동기화 복잡화 · 결국 도메인으로 이동)까지 도달

세 문항 모두 통과했다. 특히 첫 번째는 직전 세션에서 "무거운 아키텍처는 과하다"를 맞힌 뒤라 같은 방향으로 관성이 붙기 쉬운 자리였는데, 기준이 "항상 단순하게"라는 규칙이 아니라 **"단순함이 충분한가"라는 조건부 판단 축**임을 구분해냈다. 원칙을 규칙이 아니라 판단 도구로 들고 있다는 신호다.

## 안드로이드로 옮기면

이 챕터는 예시가 Swift·SwiftUI·React Native로 되어 있지만, **논지 자체는 거의 전부 그대로 옮겨진다.** 오히려 저자가 든 UI 격변 목록에 XML → Compose가 직접 들어 있어서, 안드로이드 개발자에게는 더 직접적인 이야기다.

### 오염 사례의 안드로이드 등가물

| 책의 사례 | 안드로이드에서 같은 일 |
|---|---|
| 도메인 모델을 `@Observable`로 | 도메인 모델을 `StateFlow`/`LiveData`로 노출 |
| `fetchCourses()`가 publisher 반환 | 리포지터리 메서드가 `Flow<T>`만 반환하고 일회성 조회 API가 없음 |
| `isLoading`이 도메인 메서드 책임 | `UiState(isLoading, error, data)`를 도메인 계층이 조립 |
| `@objc`·`NSObject` 침투 | 도메인 모델이 `Parcelable`·`@Entity`·`@Serializable`을 겸함 |

마지막 줄이 특히 흔하다. Room 엔티티와 Retrofit DTO와 화면 모델을 한 클래스로 겸하게 만드는 순간, **저장소 프레임워크와 네트워크 라이브러리와 UI가 동시에 그 타입의 모양을 결정**한다. 책의 표현을 그대로 빌리면 그 타입은 더 이상 순수하지 않다.

### 어댑터 패턴의 등가물

책의 구조는 안드로이드에서 이미 널리 쓰이는 배치와 정확히 겹친다.

```
:domain   CourseRepository        ← 순수 Kotlin, android.* 의존 없음
                ↑
:feature  CourseViewModel         ← StateFlow, UiState 조립 (= 책의 어댑터)
                ↑
:app      CourseScreen(@Composable)
```

`:domain`을 **순수 Kotlin 모듈(`java-library`)** 로 두면 컴파일러가 이 원칙을 강제해 준다. `android.*`를 import하려는 순간 빌드가 깨지므로, 규율이 아니라 **빌드 설정으로 분리가 유지된다.** §1.1이 말한 "규율 없이 얻는 분리"의 안드로이드판이다.

### CLI 사고 실험의 등가물

책이 말한 "실제로 출시하면 더 가치 있다"는 안드로이드에서 이렇게 실현할 수 있다.

- `:domain` 모듈에 `main()`을 두고 `./gradlew :domain:run --args="toggle-todo <id>"`
- 에뮬레이터 없이 도는 JVM 통합 테스트가 리포지터리를 직접 호출
- 디버그 빌드 전용 진입점이나 `adb shell` 명령

어느 형태든 조건은 하나다. **도메인이 `android.*`에 의존하지 않아야 가능하다.** 그래서 CLI 사고 실험은 안드로이드에서 "순수 Kotlin 모듈로 뽑을 수 있는가"라는 질문과 사실상 같은 질문이 된다. 뽑을 수 없다면 그 이유가 곧 로직이 잘못 놓인 자리를 가리킨다.

### 다만 조금 다른 것

`@Observable`에 해당하는 고민의 강도는 안드로이드가 약간 낮다. Compose의 상태 구독은 `collectAsStateWithLifecycle()`처럼 **UI 쪽에서 일방적으로 붙일 수 있어서**, 도메인 타입에 어노테이션을 요구하지 않기 때문이다. 즉 §1.4.2가 지적한 "도메인이 UI를 위해 변형된다"는 압력이 구조적으로 덜 걸린다.

그렇다고 안전한 것은 아니다. 압력은 어노테이션이 아니라 **타입 선택**으로 들어온다. 리포지터리가 `Flow`만 반환하도록 설계하면 백그라운드 워커나 일회성 동기화 코드가 어색해지는데, 이는 책이 지적한 *"백그라운드 sync에서 호출되었을 때 `fetchCourses()`가 왜 observable이어야 합니까?"* 와 정확히 같은 질문이다.

## Book 0과의 관계, 그리고 Ch2로

**Book 0이 지은 것을 Book 1이 지킨다.** Book 0은 브리핑에서 출발해 도메인 그래프를 세우고, 테스트 전략을 정하고, 의존성 주입으로 배선을 관리하는 법을 다뤘다. 그동안 UI가 한 번도 등장하지 않았던 것이 이 챕터의 전제다. 그래서 §1.1의 여섯 가지 이점은 새로운 주장이 아니라 **Book 0 전체가 이미 얻어놓은 것의 정산서**에 가깝다.

두 책의 연결이 특히 선명한 지점이 둘 있다.

- **§1.2.2의 교체 충동** 중 "비즈니스 로직을 테스트하려고 UI 테스트를 작성하게 될 때"는 Book 0 §5~§6이 다룬 문제다. 그 증상의 원인은 UI 아키텍처가 아니라 로직의 위치이며, 그래서 이 챕터의 원칙 1·3이 답이 된다.
- **§1.4.3의 어댑터**는 Book 0 §7~§8의 의존성 주입과 같은 계열의 해법이다. 둘 다 "이 타입이 저 타입을 알아야 하는가"를 묻고, 알 필요가 없다면 사이에 한 겹을 넣어 끊는다.

**Ch2로 넘어가며.** 이 챕터는 UI를 *언제* 만들지와 UI가 *무엇을 몰라야 하는지*를 정했다. 아직 다루지 않은 것은 이제 실제로 만들 UI를 **어떻게 쪼갤 것인가**다. §1.6의 마지막 항목("얇은 UI 레이어")이 약속만 하고 방법은 미뤄둔 부분이며, Ch2(Reusable Views)가 그것을 이어받는다. 첫 주제가 "이름을 그것이 *무엇인지*로 짓기"인 것도 이 챕터의 연장선이다. 뷰가 자기 이름에 특정 사용 사례를 담는 순간, §1.3이 경고한 *"한 가지 특정 사용 사례에만 사용 가능한 UI 컴포넌트"*가 되기 때문이다.
