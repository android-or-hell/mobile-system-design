# Mobile System Design — UI 9장·10장 요약

두 장은 뷰(View)와 내비게이션 흐름(Flow)의 책임을 분리하고, 각각을 다른 곳에서도 재사용할 수 있도록 설계하는 방법을 설명합니다.

- 9장: 뷰는 사용자 행동만 전달하고, 실제 내비게이션은 부모가 결정합니다.
- 10장: 흐름은 여러 화면을 연결해 하나의 기능을 완료하고, 그 결과를 부모에게 반환합니다.

두 장의 공통된 원칙은 자신이 맡은 기능은 책임지되, 자신을 사용하는 부모의 구현 방식까지 가정하지 않는 것입니다.

## 1. 9장 — 여러 내비게이션 흐름에서 뷰 재사용하기

### 1.1 뷰가 내비게이션을 직접 처리하면 재사용하기 어렵습니다

예를 들어 뷰에서 다음과 같이 화면 이동을 처리한다고 가정하겠습니다.

```
Button(
    onClick = {
        navController.navigate("settings")
    }
)
```

이 뷰는 버튼을 누르면 반드시 설정 화면으로 이동한다고 가정합니다.

하지만 동일한 뷰를 로그인 전 화면에서 사용한다면 로그인 안내가 필요할 수 있고, 다른 화면에 포함한다면 별도의 동작이 필요할 수도 있습니다.

또한 자식 뷰가 `popBackStack()` 등을 직접 호출하면 부모가 관리하는 내비게이션 상태에 영향을 줄 수 있습니다.

따라서 저자는 뷰가 특정 화면 이동을 직접 수행하지 않고, 사용자 행동만 부모에게 전달하도록 설계합니다.

```
@Composable
fun CourseView(
    onSettingsClick: () -> Unit
) {
    Button(onClick = onSettingsClick) {
        Text("설정")
    }
}
```

이제 실제 동작은 부모가 결정합니다.

### 1.2 사용자 행동을 전달하는 세 가지 방법

저자는 세 가지 접근법을 설명합니다.

| 방법      | 구현                          | 특징                           |
| ------- | --------------------------- | ---------------------------- |
| 클로저     | `onClick: () -> Unit`       | 단순하지만 액션이 많아지면 전달 코드가 늘어납니다. |
| 인터페이스   | `CourseActions`             | 여러 사용자 행동을 하나의 계약으로 관리합니다.   |
| 선언형 API | `.didPressSchedule(action)` | 필요한 액션만 설정하고 뷰를 구성할 수 있습니다.  |

여기서 중요한 것은 전달 방법보다 액션의 이름과 책임입니다.

예를 들어 `openScheduler()`는 일정 화면을 열라는 명령이지만, `didPressSchedule()`은 사용자가 일정 버튼을 눌렀다는 사실만 나타냅니다.

저자는 `CourseCoordinator`처럼 내비게이션 역할을 전제로 하는 인터페이스보다 `CourseActions`처럼 사용자 행동을 나타내는 인터페이스가 뷰의 재사용성에 적합하다고 설명합니다.

### 1.3 필요한 액션만 제공할 수도 있습니다

9장 후반에서는 선언형 API를 통해 액션을 선택적으로 제공하는 방법을 설명합니다.

```
CourseView(courseService: courseService, id: id)
    .didPressJoinCall(action: openCallFlow)
    .didPressSchedule(action: openCalendarSchedule)
```

이렇게 하면 메시지 버튼에 대한 액션을 제공하지 않았을 때 메시지 버튼 자체를 숨기는 식으로 구성할 수 있습니다.

다만 액션이 선택 사항이 되면 필수 액션을 설정하지 않아도 컴파일러가 알려주지 않을 수 있다는 단점이 있습니다. 저자는 선택적으로 구성할 수 있는 유연성과 컴파일 시점의 안전성 사이에 절충이 필요하다고 설명합니다.

9장의 결론은 다음과 같습니다.

뷰는 자신이 어느 흐름에 포함되어 있는지 알 필요가 없습니다. 사용자의 행동만 전달하면 부모가 상황에 맞는 동작을 결정할 수 있습니다.

## 2. 10장 — 견고하고 재사용 가능한 내비게이션 흐름 만들기

9장에서 개별 뷰를 재사용할 수 있도록 설계했다면, 10장에서는 여러 뷰를 연결한 흐름 자체를 재사용할 수 있도록 설계합니다.

### 2.1 흐름은 여러 단계를 연결해 하나의 기능을 완료합니다

저자는 인증 기능을 예로 듭니다.

```
AuthorizationFlow
    ├── AuthorizationIntroView
    ├── PinpadView
    └── AuthorizationResultView
```

각 뷰는 자신의 단계에 필요한 UI를 제공하고, `AuthorizationFlow`는 단계 사이의 이동을 관리합니다.

이 흐름은 결제, 계좌 등록 등 인증이 필요한 여러 기능에서 사용할 수 있습니다.

### 2.2 복잡한 처리를 부모에게 떠넘기면 안 됩니다

인증 기능에는 토큰 만료, PIN 입력 횟수 제한, 보안 SDK, 사용자 세션 관리 등의 요구사항이 있습니다.

저자는 처음에 이런 처리를 `AuthorizationHandler` 인터페이스로 정의하고 부모가 구현하도록 하는 설계를 검토합니다.

하지만 이렇게 하면 결제 기능과 계좌 등록 기능이 인증 내부의 복잡한 처리까지 알아야 합니다.

따라서 저자는 인증 기능의 복잡한 처리는 인증 도메인 내부에 두고, 부모에게는 인증을 시작하고 결과를 받는 API만 제공하도록 설계를 변경합니다.

인증 기능 내부에서는 `RateLimiter`, `SecureStorage`, `TokensSDK` 등의 객체에 책임을 나눌 수 있습니다.

### 2.3 흐름을 시작·진행·종료로 생각합니다

저자는 흐름을 하나의 이야기에 비유합니다.

시작

부모가 흐름을 생성하고 표시

진행

흐름 내부에서 화면 이동과 기능 수행

종료

완료 결과를 부모에게 반환

예를 들어 부모는 인증 흐름을 시작하고, 인증이 완료되면 성공 여부를 전달받습니다.

인증 화면이 세 개에서 다섯 개로 늘어나거나 PIN 인증이 다른 방식으로 변경되더라도, 외부 API를 유지할 수 있습니다.

저자는 이러한 구조를 가장 단순한 형태의 흐름 API로 제시합니다.

```
// 원문의 설계를 Kotlin 의사코드로 표현
AuthorizationFlow(
    config = config,
    onCompleted = { result ->
        // 부모가 결과에 따라 처리
    }
)
```

필요하다면 사용자, 네트워크 의존성, 안내 문구 등의 설정을 추가할 수 있습니다. 설정 항목이 많아지면 별도의 `Config` 타입으로 묶는 방법도 제시합니다.

10장의 결론은 흐름 내부 구현은 감추고, 부모에게 필요한 의존성·설정과 완료 결과만 외부 API로 제공하는 것입니다.

## 3. 9장과 10장을 함께 적용하면

두 장의 책임 관계를 하나의 구조로 나타내면 다음과 같습니다.

PaymentFlow (부모 흐름)

결제 과정 관리 · 인증 시작 · 결과 처리

인증 시작

AuthorizationFlow (하위 흐름)

인증 절차와 내부 상태 관리

안내 View

PIN View

결과 View

각 View는 사용자 행동만 전달하고, Flow가 단계 이동을 결정합니다.

인증 완료 결과 반환

PaymentFlow

인증 결과에 따라 결제 과정 진행

여기서 책임을 구분하면 다음과 같습니다.

| 구성 요소   | 책임                         | 알 필요가 없는 것            |
| ------- | -------------------------- | --------------------- |
| View    | UI 표시, 사용자 입력 감지와 행동 전달    | 부모의 내비게이션 구조          |
| Flow    | 여러 단계를 연결하고 기능 완료까지의 과정 관리 | 자신을 사용하는 부모의 전체 업무 흐름 |
| 부모 Flow | 하위 흐름 시작, 결과 수신 및 후속 처리    | 하위 흐름의 내부 화면·구현 세부사항  |

중요한 것은 독립적인 기능을 만들기 위해 모든 책임을 하나의 클래스에 넣어야 하는 것은 아니라는 점입니다.

`Flow`는 내부의 여러 뷰와 객체를 조합할 수 있습니다. 외부에 복잡한 구현을 노출하지 않는 것이 핵심입니다.

## 4. 두 장의 핵심 설계 원칙

1. View는 사용자 행동을 전달합니다. 특정 화면으로 이동하거나 부모의 내비게이션 상태를 직접 변경하지 않도록 합니다.
2. Flow는 기능의 진행을 관리합니다. 여러 화면을 연결하고 필요한 내부 처리를 조정합니다.
3. Flow는 기능의 목적에 맞는 결과를 반환합니다. 부모는 그 결과를 받아 자신의 업무를 계속 진행합니다.
4. 복잡한 내부 구현은 외부 API에 노출하지 않습니다. 내부 로직은 필요한 객체로 나누되, 부모가 알아야 하는 계약은 단순하게 유지합니다.
5. 구현 기술보다 책임의 경계를 먼저 결정합니다. 콜백, 인터페이스, Coordinator, Router 등의 선택은 그다음 문제입니다.

마지막으로 두 장의 차이를 한 문장씩 정리하면 다음과 같습니다.

9장은 “뷰가 부모의 내비게이션을 결정하지 않도록 설계하는 방법”이고, 10장은 “부모가 하위 흐름의 내부 구현을 책임지지 않도록 설계하는 방법”입니다.

이 두 원칙을 함께 적용하면 개별 뷰와 전체 기능 흐름을 서로 다른 화면이나 기능에서도 재사용하기 쉬운 구조로 만들 수 있습니다.
